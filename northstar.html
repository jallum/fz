Incremental Fact Compiler

The compiler is one world of stable ids, immutable source-owned definitions, and derived facts. Code and runtime modules are referenced first and defined later. Direct facts settle through exact waits, and product-keyed artifact pulls ask only for the executable products a submitted root actually reaches.

There is one fact engine and one retained product session per requested root. Activation inputs, return types, callsite summaries, and keying facts settle as direct facts. Backend artifacts are root-local products that wait on exact facts or products; they never begin from a root-wide collection pass. Interpreter, native, and macro consumers project the retained answer through one boundary, so the backend value and the fact movement that produced it move in lockstep.

This page is the world model in one sitting. The subsystem detail lives in .agent/docs; each section below names the doc that owns its detail.

Goal, Signal, Strategy

Goal

Submit code, submit a root, and derive exactly one backend-owned answer from the smallest executable product set demanded by that root. Unused user functions and unused runtime library functions stay cold. Compile work is proportional to the input.

Signal

Tests assert both presence and absence: which modules were defined, which activations existed, which callsites were selected, which product keys were requested, and which functions never warmed. The telemetry stream is the evidence: which jobs ran and why they started, which facts moved revision, and how many times each activation's return was defined or widened.

Strategy

Keep stores small and facts honest. One logical fact gets one fact key. A revision moves only when the published answer changes. Everything else is a consequence of that.

Core Shape

The world owns all durable identity domains. Definitions live in typed stores. Recomputable answers live in the work graph, which is one field of the world, not a service beside it. Types are not an external service either; they are one more compiler-owned store. The stores are many and specific, one per fact family, so a fact key names exactly one store entry and nothing is looked up twice.

Stable ids first

Source owners, modules, functions, type names, and roots are minted the moment they are referenced. Referencing a module or MFA before its definition creates a placeholder, never a failure. Definition arrives later as a fact.

Local type world

The world owns one interner. Every Ty is a u32 handle meaningful only inside that world, and interning is canonical by construction: two descriptors that denote the same set mint one id. Facts detect change by comparing ids, so no fact ever hashes a type structurally.

No parallel phase graph

The only scheduler abstraction is the work graph. The loop reaches a fixpoint because job keys coalesce, cumulative facts join contributions, and changed revisions wake exactly the jobs that read or waited on those slots.

When a settled prerequisite asks the drained graph to resolve a cycle, finality belongs to each publishing job and its co-outputs. Other publishing jobs keep their own claims; unsettled external-product ground prevents certification. Later dependency movement unfinalizes the same claims through the ordinary work graph.

Source, Scope, And Runtime Bootstrap

Every job is a rule: it reads some facts, waits on the ones it cannot read yet, and publishes the facts it owns. Jobs come in tiers that only ever read downward. The source tier indexes a submission, scopes it, and defines modules, module interfaces, functions, type names, struct layouts, and function contracts; macro expansion sits inside it, one expanded source per function. The lowering tier turns one function into a lowered body, its guard and entry dispatch plans, its static callees, its call-graph component, and its input demand. The semantic tier seeds roots and activations and analyzes one activation at a time. The executable tier derives per-executable facts and runtime demand. Artifacts are pulled separately by product key and are not jobs at all.

Parsing and top-level discovery are eager only at the code-contribution boundary. Indexing one submission parses it, stores its top-level items on the source record, and discovers nested module ids. It does not define functions, lower bodies, or pull imports. Scoping then walks the parsed items in source order twice: the first pass reserves local functions and child modules so later definitions can reference them; the second applies order-dependent items, which are aliases, imports, function definitions, protocol surfaces, and child-module scope points.

The runtime prelude is ordinary code, not a mode. Constructing a world stores the prelude source as compiler-owned text and creates named runtime module placeholders; no lexing or parsing happens yet. The first user submission waits on the prelude being scoped, scopes it into a namespace head, saves that head, and scopes user code against it. Further preludes, such as the one that defines the test item macro, scope in over the runtime prelude by the same rule. 

prelude source stored on its source owner
            │
            ├─ no lexer/parser work at construction time
            │
first user ScopeCode(source)
            │
            ├─ wait on CodeScoped(runtime prelude)
            ├─ ScopeCode(runtime prelude)
            ├─ save the prelude namespace head
            └─ ScopeCode(user source) with that head as the base namespace

Runtime modules warm lazily too. Referencing Enum.reduce/3 allocates ids immediately. The library source that owns Enum is submitted and indexed only when a demanded scope, import, protocol edge, or call edge requires it.

Namespace Model

A namespace is a linked list with integer savepoints. Binding zero is the end sentinel. Pushing a binding returns a new head. Leaving a scope means restoring an older head. Lookup walks backward and the first matching binding wins. A binding names one of six symbol kinds: a module, a function, a macro, a callable that may be either, a type name, or a quoted splice that macro expansion substitutes in place.

Imports and aliases are therefore ordinary scope mutations. Exact import ..., only: clauses bind module/function references immediately without forcing the provider surface. Plain import waits until the provider module's interface is defined so exports can be copied correctly and missing imports can surface as diagnostics when the drive goes quiet.

Facts And Revisions

A fact slot records who claims the fact and a revision. It holds no value: the typed value lives in the world store the key names, and the slot gates its visibility. The revision is the wake-up signal. There is no separate fingerprint layer. A publisher is one job's derivation, so a job that concludes several answers in one run owns each of them separately and a later run can retract one without disturbing the others.

Facts come in two shapes. A replacing fact has one answer that a fresh run overwrites. A cumulative fact joins the contributions of every publisher, and absence is bottom: a claim at bottom is a real claim with revision zero, so "nobody has said anything yet" is readable and distinct from "the answer is empty". Activation inputs are the model case: each call contributes a whole input row, rows join as a set of alternatives, and a wider row covers the rows it dominates. Joining columns across rows would invent calls that never happened, so it never happens.

Work Graph

The work graph is one agenda, one fact table, and one dependency index. The agenda is deduplicated: a job queued ten times while pending runs once, and a job whose facts move after it ran is queued again. Jobs record what they read, what they could not read yet, and what they output. No job enqueues a follow-up job of its own; a job that cannot proceed records a bare wait, and the fact-to-producer map is the sole path that restarts blocked work. Every work start carries its reason, so the trace can say why a job ran. 

while let Some(job) = agenda.pop() {
    let effects = run(job)?;
    let step = work_graph.complete(job, effects);

    changed facts wake:
      - subscribers that previously read them
      - waiters that previously blocked on them
}

A drive ends only when nothing more can be demanded. It resolves when the agenda is empty and no wait remains. It is unresolved when exact waits remain with no producer to map them to, and world-derived diagnostics are emitted from that frontier. A failed product dependency, a job error, and an exhausted deadline each end the drive on their own terms, and none of them is a fact: errors are loud, never joined into the table.

Detail: fact-engine.md, performance-instrumentation.md.

Activation Keys And The Local Type World

An activation is one function specialized for one root at one canonical input shape. Its key holds the root, the function, and one interned arrow whose parameter side is the canonical inputs and whose result side is an address variable, the return not yet known. Equal structure inside one world means equal ids, so activation keys, callsite summaries, and fact joins lean on exact id equality instead of deep structural hashing.

Keying waits for two function facts, named in one ask:

  • Recursive(function) says whether the function sits on a cycle of the static call graph, and whether its body consumes the identity of a callable it is handed. It is a projection of the same walk that publishes the function's call-graph component.
  • InputDemand(function) says which inputs the activation's published return can depend on, over three axes. Local dispatch is what this body's own entry dispatch asks of a slot. Forwarded dispatch joins that with the demand of every callee this body hands the slot to unchanged, because the value that arrives decides which callee activation is reached. Returned is the other way a return depends on an input: the returned value is, contains, or projects that slot, minus the positions the recursion itself supplies. A slot no axis reaches is freight and collapses, so two callers key one activation there.

Each demand axis is one least fixpoint over the body's forwarding cone. Only after both facts exist does the world canonicalize a call's inputs: address the whole input vector once, then either erase transported closure identities on the slots no dispatch reads, or, on a recursive function, collapse the arrow by the forwarded and returned axes so the specialization stays finite. That is what keeps recursion bounded without a second hidden type loop.

Type Naming And The Surface Tier

A type name in source — integer, Enumerable.t, SomeModule.t — is a name, not a type. Representing a type and naming one are different jobs. World.types represents: it mints and compares set-theoretic symbols and is ignorant of what the language calls them, so a Ty carries its own content and the lattice never consults a name table. Naming is reference and definition, so it is fact work like everything else.

name → (namespace) → identity → (fact) → Ty. The same path an MFA takes, applied to types.

Namespace is the bridge

A type-position name resolves through the same binding chain as a value name. NamespaceSymbol::Type(TypeName) binds a name to an identity, never to a resolved type, so it can be named before it is defined.

Identity carries arity

TypeName { module, name, arity } keys on the owning module id, so t in-module and Mod.t from outside are one identity. t/0 and t/1 are not.

Definition is a fact

TypeDefined(TypeName) publishes the resolved Ty from a typed store with a Presence revision. A spec waits on it like any other fact. 

@spec foo(SomeModule.t(float), integer) :: integer

index:   mint ModuleId(SomeModule), TypeName(SomeModule, "t", 1)
         demand DefineModule(SomeModule)              -- reference before define
surface: DeriveTypeDef -> TypeDefined(SomeModule,"t",1) = hard Ty
         DeriveFunctionContract(foo) waits on it -> FunctionContract(foo)

Type denotation is a surface-tier fact: it depends only on indexing and definition, never on activations, return types, or callsite summaries. Every dependency edge runs one way — index, surface, semantic, artifact — so by the time artifact products ask semantic questions, every type name is already a hard Ty. The semantic tier reads types; it never moves a denotation.

Two consequences keep the symbol self-contained and the program minimal. A nominal type carries its own inner: @type Meters :: refines integer mints a Ty whose axes already hold the integer representation, so is_subtype(Meters, integer) reads from structure and no name table is threaded into the lattice. And a protocol domain is a marker, not a union: Enumerable.t depends only on the protocol declaration, while which impls reach the program is decided by demand-driven dispatch as concrete values flow to protocol positions. The implementation relation is closed — "does this type implement it?" has a fixed answer — but the implementers are never enumerated up front: a program that never mentions a Range never pulls the Range impl, and only the callbacks actually called are lowered.

Product Pulls And Artifact Projection

Activation analysis publishes callsite summaries, reached callee activations, executable needs, a joined return type, and atomic entry reachability, which is the reachable clauses plus whether dispatch failure remains possible, for one rooted activation. Artifact producers consume the settled facts derived from that analysis directly: if a prerequisite is not settled, the producer returns an exact fact wait; if another artifact is needed, it returns a product wait. 

RootBackendProduct(root)
  waits on RootEntry(root), Recursive(entry), InputDemand(entry)
  pulls BackendExecutable(entry E)

BackendExecutable(E)
  pulls AbiExecutable(E) and the AbiExecutables its call edges reach

AbiExecutable(E)
  pulls MaterializedExecutable(E)
  pulls ExecutableEffects(E)
  pulls TransportShape(entry capture / input / return / resume / value positions)
  pulls CallableConstruction(callable positions)

MaterializedExecutable(E)
  waits on settled ExecutableFacts(E), ReturnType(E.activation), RuntimeDemand(E)
  pulls TransportShape(ExecutableReturn(E))

Materialization takes the shared lowered body, enters a sole reachable clause directly only when failure is unreachable, prunes unreachable clauses, rewrites semantically cold local-control entries into explicit halt stubs, and freezes each live callsite to its selected typed callee executable keys. Each backend producer records membership edges for its local calls, positioned callable targets, and reachable schemas. The memo maintains root membership over those committed edges and supplies changed keys to packaging, and persistent ordered inventories share untouched branches with older snapshots. Root assembly never traverses all retained bodies to rediscover membership.

Product freshness is revisioned by exact product generations and exact fact uses. A producer records each dependency at the read site; a wait only names a dependency already recorded. The scheduler passes one final fact movement per moved key to a reverse index, and only the retained roots that read that fact receive it, including dormant roots and roots suspended around a nested macro drive. The memo's reader index emits a subscription change only as a fact's first reader appears or its last reader leaves, so delivery scans neither roots nor dependencies. The world retains one product session per root, user or macro; the session's memo owns the artifact answers, and retiring the root releases both.

Physical layout is owned by positions, not by types. Each transport position owns one layout answer, derived from settled runtime demand, the executable's facts, and exact upstream position products; recursive positions settle as one atomic group from their external anchors. A layout is structural shape plus carrier presence, and encoders obey the carrier before inspecting the shape: a carrier consumes one typed value lane, an absent carrier walks the recursive layout. A field's carrier and its parent tuple's carrier are separate, so an unboxed tuple stays decomposed even when one child is boxed. Where a value's layout puts its fold is unobservable to the program, and no test asserts on it.

Callables keep the same discipline. A positioned construction owner separates direct callable facts from first-class wrapper authority; direct-only positions carry no construction. Private callable targets keep their exact return layouts, and a first-class wrapper publishes one uniform contract, diverges, absent, or one value reference, for every nonempty returning result. Callers never infer a return contract by scanning targets, types, or the semantic world. A caller owns its return payload position; the callee independently owns its executable return.

The root product owns one shared backend program and applies exact rooted executable, wrapper, atom, and schema contribution changes. The native program is the last compiler-owned artifact before JIT and AOT; shared native codegen asks it only backend-consumption questions, and any semantic, reachability, or type answer it still needs after materialization becomes a named fact or product, never an adapter-side query back into the semantic world. The interpreter consumes the backend program, the JIT and AOT doors consume the native program, and one command-line front door serves all three.

Worked Example: Quicksort Plus foo/0

A function body is not a list of steps plus a final result. It is a small entry graph.

  • LoweredClause owns head projections and points at the ControlEntryId where its body starts.
  • LoweredEntry is one reusable local control node: captured inputs, straight-line steps, and one tail.
  • LoweredTail is the only place control can branch, call, or return.
  • ControlDestination says whether a value returns from the executable or is delivered into another local entry.

A non-tail call needs no hidden "finish the rest of the block" machinery. It names the resume entry that receives the result: 

entry N:
  steps...
  tail = DirectCall { ..., dest: Deliver(resume_k) }

entry resume_k:
  origin = DeliveredResume { value: v }
  captures = [...]
  steps...
  tail = ...

Clause bodies originate as Clause. Compiler-made joins and branch arms originate as Branch. A receive arm originates as ReceiveOutcome. Any entry that receives a delivered value, whether from a non-tail call or from local control that never crosses a callable boundary, originates as DeliveredResume { value }. Backend and native lowering consume this explicit control graph mechanically instead of recovering it later from positional tailness. The backend interpreter preserves the same model: a direct tail call may park on receive, and the blocked task keeps a backend continuation stack so the eventual wake can still deliver back into the caller's resume entry.

01Discovery is cheap

The bracketed inputs below are shorthand for the key's interned arrow. Submit quicksort plus an extra top-level def foo(), do: 42. The first drive only runs IndexCode. It parses the source, stores the top-level items, and publishes CodeIndexed(code). No functions are defined yet. No bodies are lowered. No activations exist.

02Demanding main/0 scopes only what the root needs

Submit root {GLOBAL, main, 0, Value}. The next drive scopes runtime:runtime.fz, saves the prelude namespace head, scopes the user code, and publishes: 

FunctionDefined(main/0)
FunctionDefined(qsort/1)
FunctionDefined(partition/4)
FunctionDefined(append/2)
FunctionDefined(foo/0)
RootEntry(root)

Still absent: LoweredBody(foo/0), any Activation(... foo ...), and any runtime module surface unrelated to the root.

03The root seed starts the first activation

SeedRoot(root) waits until FunctionDefined(main/0), Recursive(main/0), and InputDemand(main/0) exist, then publishes the entry demand facts and contributes the root's own runtime demand for the entry executable: 

Activation(root, main/0, [])
ActivationInputs(root, main/0, []) = { [] }
Executable(root, main/0, [], Value)

The artifact path does not rely on self-scheduled follow-up work. When the interpreter asks for RootBackendProduct(root), the product driver waits on the exact facts needed to key the entry executable and then pulls BackendExecutable(main/0[]). A second request for a root whose session is already active is parked and re-enqueued when that session restores, on success and on failure alike.

04Activation analysis co-derives types and plans

AnalyzeActivation(root, main/0, []) lowers nothing new beyond main/0's own body and follows only dispatch-reachable clauses. It publishes one whole summary per callsite. The summary names each selected callee, the surface inputs the call sends, the exact activation it reached, and the return it has seen: 

CallSiteSummary(root, main/0[], qsort_call) =
  { targets: [ { callee: qsort/1,
                 surface_inputs: [non_empty_list(int)],
                 activation: qsort/1[[int]],
                 return: [int] } ],
    return: [int] }

The same body's calls to Kernel.dbg/1, Process.heap_alloc_stats/0, and Kernel.+/2 publish summaries of the same shape; they are ordinary runtime functions reached by ordinary call edges. That same job also contributes: 

Activation(root, qsort/1, [[int]])
Executable(root, qsort/1, [[int]], Value)
ReturnType(root, main/0, []) = int | float
ActivationAnalyzed(root, main/0, [])

05Recursive inputs settle by keying, then by joined rows

main/0 hands qsort/1 a non-empty literal list, but qsort/1 is recursive, so keying collapses its arrow to the shape the recursion converges on. The entry call and both recursive calls key one activation, qsort/1[[int]]. partition/4 shows the other collapse: no dispatch reads its two accumulator slots and the recursion itself supplies what it returns in them, so those slots are freight and key as variables. 

partition/4[int, [int], [a2_e], [a3_e]]
  from qsort/1:      partition/4(int, [int], [], [])       -- first row
  from partition/4:  partition/4(int, [int], [int], [int]) -- recursive rows
  retained rows:     one activation, one joined ActivationInputs

Each call contributes a whole input row to ActivationInputs for the selected activation. Arguments that arrived together stay together. If two calls share an activation but supply different pairs, both pairs remain alternatives; combining their callsite summaries does not invent a third call containing every mixture of those arguments. Changed input evidence wakes the analysis through the same fact graph.

06Tuple-field need rides on the executable key

The call from qsort/1 to partition/4 destructures the result, so the executable it demands carries that need in its key: 

Executable(root, partition/4, [int, [int], [a2_e], [a3_e]], TupleFields(2))

The need is part of the executable's identity and of the runtime demand callers contribute to it. There is no separate ReturnNeed fact to keep in sync.

07Product demand excludes foo/0

When RootBackendProduct(root) pulls the entry backend executable, products follow only the typed membership edges recorded by demanded executable products: 

RootBackendProduct(root)
  entry: main/0[]
  products: BackendExecutable(main), BackendExecutable(qsort), BackendExecutable(partition),
            BackendExecutable(append),
            ...the Kernel and Process executables named by main/0's call edges,
            and the runtime helpers those name in turn...

foo/0 is absent because no reached callsite ever referenced it, so no product key asks for its body or backend executable.

08Products freeze and package only demanded executables

MaterializedExecutable(E) takes the shared lowered body, prunes unreachable clauses, rewrites semantically cold local-control entries into explicit halt stubs, and records symbolic call edges. AbiExecutable(E) then settles the parameter representations, the semantic input layouts, the return layout and every return endpoint, the transport plan, per-value layouts, effects, ABI-ready call edges, and positioned callable construction owners, without asking new semantic questions. BackendExecutable(E) reads its own ABI product and the ABI products its call edges name, then lowers one retained body and records its callee and schema membership. Finally, RootBackendProduct(root) applies exact executable and schema changes, retains their positioned transport plan, and shares their allocations in BackendProgram.

The session and its dependency graph remain owned by Compiler2 after the request. Asking again without a movement cache-hits this exact root answer and evaluates no producer. Redefining uncalled foo/0 later does not change that root product. Redefining main/0 can, because the settled local callsite summaries it depends on may change. Retiring the root releases the session and its movement subscriptions.

Worked Example: Enum.reduce

01Prelude scope is enough to name runtime APIs

A user function can call Enum.reduce/3 with no eager runtime parse at construction time. The first demanded scope pulls runtime.fz, binds the prelude namespace, and lets user source resolve Enum as a module id.

02The root only warms the reached runtime surfaces

When main/0 calls Enum.reduce/3, AnalyzeActivation(root, main/0, []) publishes: 

CallSiteSummary(root, main/0[], enum_reduce_call) =
  { targets: [ { callee: Enum.reduce/3,
                 surface_inputs: [[int], int, (int, int) -> int],
                 activation: Enum.reduce/3[non_empty_list(int), int, closure[main/0#lambda@0/2]],
                 return: int } ],
    return: int }

Enum.reduce/3 is not recursive, so nothing collapses the literal's non-empty shape, and its body constructs a lambda, which makes it consume callable identity, so the exact closure stays in the key. That summary contributes the rooted activation, and only then does the engine submit and define the runtime module surface that owns the function.

03Protocol dispatch is still ordinary fact work

Enum.reduce/3 wraps the accumulator as {:cont, acc}, mints a bridge lambda that calls the user's reducer and rewraps its result, and calls the protocol callback Enumerable.reduce/3. The receiver type is a list, so that callsite devirtualizes to Enumerable.List.reduce/3 directly. No activation exists for the protocol callback itself, and its placeholder body is never lowered. Each reached hop publishes one whole callsite summary and one callee activation: 

CallSiteSummary(root, Enum.reduce/3[...], protocol_call)
  => Enumerable.List.reduce/3[non_empty_list(int), {:cont, int}, closure[Enum.reduce/3#lambda@0/2]]
  => List.reduce/3                       -- the impl delegates
  => List.reduce_step/3, List.reduce_cont/3
ReturnType(root, Enum.reduce/3#lambda@0/2, [...]) = {:cont, int}
ReturnType(root, Enum.reduce_finish/1, [{:done, int}]) = int

04User closures become ordinary generated functions

The reducer lambda is lowered into a generated function id owned by the enclosing user function. Its activation and return type live in the same fact families as named functions: 

FunctionDefined(main/0#lambda@0/2)
LoweredBody(main/0#lambda@0/2)
Activation(root, main/0#lambda@0/2, [int, int])
ReturnType(root, main/0#lambda@0/2, [int, int]) = int

05Unreached runtime code stays cold

The final root product contains only the user function, the reducer lambda, and the reached runtime and protocol helpers. Enum.map/2 and Enum.reverse/1 are defined but never analyzed, and the Map and Range implementation modules are never defined at all, so none of them get product keys and none reach materialization.

Observability And Guideposts

Telemetry carries raw ids, facts, and opaque structures. Formatting belongs in handlers. The compiler surface emits spans for the drive and each job, each carrying the reason the work started, plus state-defining events such as function.defined, callsite.defined, return_type.defined and return_type.widened, retained artifact settlements through pull.product.settled, product dependency movements through work_graph.dependencies_moved, and pull.session.finished. Tests observe those events instead of poking through world internals.

Every presentation keeps three answers apart. Unknown is a return not yet published; it is bottom, the join identity, and it is rendered as unpublished. None is a computed empty type. Any is a computed top. A dump or trace that prints one of these with another's word has lost the distinction the fixpoint exists to make.

Summary tests

src/compiler2/drive_test.rs is the fast contract surface. The quicksort, Enum.reduce, and variadic-extern tests assert finite closure size, exact reached callsites, absence of cold helpers, and the pulled backend and native products.

Useful rerun: cargo test --lib compiler2_

Trace and distill

fz2 --log-telemetry <path> appends the JSONL stream for one run; --emit=stats prints the settle counts on exit. The distiller sums inclusive and self time by span, by job kind, and by the function served, and counts return definitions and widenings per activation.

Useful rerun: elixir tools/distill-telemetry.exs trace.jsonl

What to watch

The important numbers are not raw event counts in isolation. They are: which jobs were coalesced, which facts changed revision, which waits remained unresolved, how many times a return was defined, and which roots reclosed after a redefinition. On a trivial fixture, a slow compile is a correctness signal, not a performance one.

Detail: telemetry.md, performance-instrumentation.md, canonical-form.md, fixtures.md. The activation dump does not yet render an unpublished return as unpublished; that repair is fz-kdt.177.19.

North Star Checklist

  • Stable ids before meaning: modules and MFAs can be referenced before they are defined.
  • One local type world: Ty is compiler-owned and never compared across worlds.
  • One id per denotation: interning is canonical by construction, so equal sets are equal ids and a canonical rendering is for display only.
  • Represent, don't name: Types carries no naming duty; a type name is an identity defined by TypeDefined, settled at the surface tier before any semantic question is asked.
  • One logical fact, one key: whole callsite summaries replace split partial facts.
  • No separate type loop: activation-input joins are ordinary cumulative facts.
  • Unknown, none, and any stay apart: bottom is a readable claim, never the empty type, in every fact and every presentation.
  • Lazy runtime bootstrap: the prelude and the runtime library warm only when demanded.
  • Product-keyed artifacts: artifact producers return exact fact and product waits; nothing self-schedules follow-up work.
  • Artifact isolation: materialization consumes settled local facts and named products, then final root packaging follows and shares only exact reachable backend product values.
  • Blast radius by revision: redefinition propagates only as far as fact revisions actually change.
  • Work proportional to input: the trace says why every job started; excess work is a defect, not a cost.

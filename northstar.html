Incremental Fact Compiler

The compiler is one world of stable ids, immutable source-owned definitions, and derived facts. Code and runtime modules are referenced first and defined later. Direct facts settle through exact waits, and product-keyed artifact pulls ask only for the executable products a submitted root actually reaches.

There is one fact engine and one product driver. Joined activation inputs, return types, direct-call summaries, and recursive keying facts settle as direct facts. Backend artifacts are request-local products that wait on exact facts or products; they do not begin from a root-wide semantic closure pass.

Goal, Signal, Strategy

Goal

Submit code, submit a root, and derive exactly one backend-owned answer from the smallest executable product set demanded by that root. Unused user functions and unused runtime library functions stay cold.

Signal

Tests assert both presence and absence: which modules were defined, which activations existed, which callsites were selected, which product keys were requested, and which functions never warmed.

Strategy

Keep stores small and facts honest. One logical fact gets one fact key. Slot revisions bump only when the aggregate value changes. Everything else is a consequence of that.

Core Shape

The world owns all durable identity domains. Definitions live in stores. Recomputable answers live in the work graph. Types are not an external service; they are one more compiler-owned store. 

struct World {
    tel: Telemetry,

    code: CodeMap,
    modules: ModuleMap,
    functions: FunctionMap,
    namespaces: NamespaceStore,
    types: Types,
    roots: RootMap,

    bodies: LoweredBodyMap,
    guard_dispatches: GuardDispatchMap,
    entry_dispatches: EntryDispatchMap,
    recursive: RecursiveMap,
    dispatch_masks: DispatchMaskMap,

    activations: ActivationMap,
    callsites: CallSiteMap,
    backend: BackendProgramMap,

    work_graph: Scheduler<Job, FactKey>,
}

Stable ids first

CodeId, ModuleId, FunctionId, and RootId are minted immediately. Referencing a module or MFA before definition creates a placeholder instead of a failure.

Local type world

World.types owns one compiler-local Types store. Every Ty is an interned u32 handle meaningful only inside that one world. Shared helper modules talk to it through trait compatibility at the seam.

No parallel phase graph

The only scheduler abstraction is the work graph. The loop reaches a fixpoint because job keys coalesce, fact slots join contributions, and changed revisions wake exactly the jobs that read or waited on those slots.

The artifact boundary is product-keyed: MaterializedExecutable(E) then AbiExecutable(E) then BackendExecutable(E), with RuntimeDemand(E), ExecutableEffects(E), TransportShape(position), and callable / boundary facts pulled only when a demanded executable names them. The final RootBackendProduct(root) packages request-local symbolic executables into one dense BackendProgram.

Source, Scope, And Runtime Bootstrap

Parsing and top-level discovery are eager only at the code-contribution boundary. IndexCode parses one code submission, stores top-level items on the code record, and discovers nested module ids. It does not define functions, lower bodies, or pull imports. 

enum Job {
    IndexCode(CodeId),
    ScopeCode(CodeId),
    DefineModule(ModuleId),
    LowerFunction(FunctionId),
    ReifyGuardDispatch(FunctionId),
    PlanEntryDispatch(FunctionId),
    DeriveRecursive(FunctionId),
    DeriveDispatchMask(FunctionId),
    SeedRoot(RootId),
    AnalyzeActivation(ActivationKey),
    BuildMacroExecutable(FunctionId),
    LowerNativeProgram(RootId),
}

The full enum still contains legacy semantic-closure and root transport-plan jobs for diagnostic dump surfaces and old contract tests. They are not the artifact vocabulary: backend products are pulled by ProductKey and exact settled fact waits.

ScopeCode then walks the parsed items in source order. The first pass reserves local functions and child modules so later definitions can reference them. The second pass applies order-dependent items: aliases, imports, function definitions, protocol surfaces, and child-module scope points.

The runtime prelude is ordinary code, not a mode. World::new stores runtime:runtime.fz as compiler-owned code text and creates named runtime module placeholders. No lexing or parsing happens yet. The first non-runtime ScopeCode waits on CodeScoped(runtime_prelude), scopes that source into a namespace head, saves the resulting prelude_head, and then scopes user code against it. 

runtime.fz stored in CodeMap
            │
            ├─ no lexer/parser work at construction time
            │
first user ScopeCode(code)
            │
            ├─ wait on CodeScoped(runtime_prelude)
            ├─ ScopeCode(runtime_prelude)
            ├─ save NamespaceStore.prelude_head()
            └─ ScopeCode(user_code) with that head as the base namespace

Runtime modules warm lazily too. Referencing Enum.reduce/3 allocates ids immediately. The runtime source containing Enum is only submitted and indexed if a demanded scope, import, protocol edge, or call edge requires it.

Namespace Model

A namespace is a linked list with integer savepoints. BindingId(0) is the end sentinel. Pushing a binding returns a new head. Leaving a scope means restoring an older head. Lookup walks backward and the first matching binding wins. 

type Namespace = BindingId;

struct NamespaceStore {
    bindings: Vec<Binding>,
    prelude_head: Namespace,
}

struct Binding {
    name: String,
    symbol: NamespaceSymbol,
    prev: Namespace,
}

enum NamespaceSymbol {
    Module(ModuleId),
    Function(FunctionId),
    Macro(FunctionId),
}

Imports and aliases are therefore ordinary scope mutations. Exact import ..., only: clauses bind module/function references immediately without forcing the provider surface. Plain import waits until the provider module is actually defined so exports can be copied correctly and missing imports can surface as diagnostics when the drive goes quiet.

Facts And Revisions

A job owns contributions. A fact slot owns the current aggregate value plus a revision. The revision is the wake-up signal. There is no separate fingerprint layer. 

struct FactSlot<Job> {
    value: Option<FactValue>,
    revision: u64,
    contributions: HashMap<Job, FactValue>,
}

enum FactValue {
    Presence(u64),
    Inputs(Vec<Ty>),
}

Presence joins by max. Inputs joins pointwise with Types::refine_widen, then alpha-normalizes through the world-owned type store. This is the whole trick: activation inputs settle by the same mechanism that tracks all other fact replacement.

Family Current facts Meaning
Source surface CodeIndexed, CodeScoped, ModuleIndexed, ModuleDefined, FunctionDefined Discovery and scope are separate. Indexing finds ids. Scoping/definition publishes the usable surface.
Lowering and dispatch LoweredBody, GuardDispatch, EntryDispatch, Recursive, DispatchMask Reusable function facts that make semantic keying and activation analysis deterministic.
Root seed RootEntry, Activation, Executable The root grows a frontier of demanded activations and demanded executable shapes.
Semantic ActivationAnalyzed, ReturnType, CallSiteSummary Type and plan facts are one family. A callsite summary carries selected callee, joined input types, executable need, and return type together.
Product root RootBackendProduct(root) The demanded root answer. It keys the entry executable, pulls symbolic backend executables by product key, and packages only the request-local inventory.
Executable products MaterializedExecutable(E), AbiExecutable(E), BackendExecutable(E) Per-executable artifact products. Each producer waits on exact local facts or product keys and never schedules unrelated work.

RuntimeDemand and ExecutableEffects are SCC-settled: each producer discovers its cyclic dependency group from settled call-edge facts, runs a bottom-start monotone ascent to the fixpoint entirely inside the producer, and publishes the settled value for every member at once — no mid-ascent value is ever observable.

One logical fact gets one key. There is no split SelectedCallee / ReturnNeed pair anymore. Consumers read one CallSiteSummary surface and react when that one revision changes.

Work Graph

The work graph is one agenda, one fact table, and one dependency index. Jobs record what they read, what they could not read yet, and what they output. No job enqueues a follow-up job of its own; a job that cannot proceed records a bare wait, and the fact->producer map (World::demand_fact_producer) is the sole path that restarts blocked work. 

struct Scheduler<Job, Fact> {
    agenda: Agenda<Job>,
    facts: FactTable<Job, Fact>,
    deps: DependencyIndex<Job, Fact>,
}

struct Agenda<Job> {
    queue: VecDeque<Job>,
    queued: HashSet<Job>,
}
while let Some(job) = work_graph.pop() {
    let effects = run(job)?;
    let step = work_graph.complete(job, effects);

    changed facts wake:
      - subscribers that previously read them
      - waiters that previously blocked on them
}

The outer drive loop has only three outcomes:

Resolved

The agenda is empty and there are no unresolved waits.

Unresolved

The agenda is empty but the dependency index still has exact waits. World-derived diagnostics are emitted from that frontier.

Fatal

A job hit a coarse failure. Diagnostics already flowed through telemetry. The drive stops immediately.

Activation Keys And The Local Type World

Ty is an interned u32 id inside World.types. Equal structure inside one world means equal ids. That lets activation keys, callsite summaries, and fact joins lean on exact id equality instead of deep structural hashing. 

#[repr(transparent)]
struct Ty(u32);

struct Types {
    interner: TypeInterner,
    comparisons: ComparisonCache,
}

Activation keying waits for two function facts:

  • Recursive(function) tells keying whether recursive non-dispatch inputs should collapse by convergence class.
  • DispatchMask(function) tells keying which entry inputs matter for dispatch at all.

Only after both exist does World::activation_key canonicalize inputs through: widen_for_recursive_spec_key, optional convergence-class collapse, and final alpha_normalize_vars. That is what keeps recursion finite without a second hidden type loop.

Type Naming And The Surface Tier

A type name in source — integer, Enumerable.t, SomeModule.t — is a name, not a type. Representing a type and naming one are different jobs. World.types represents: it mints and compares set-theoretic symbols and is ignorant of what the language calls them, so a Ty carries its own content and the lattice never consults a name table. Naming is reference and definition, so it is fact work like everything else.

name → (namespace) → identity → (fact) → Ty. The same path an MFA takes, applied to types.

Namespace is the bridge

A type-position name resolves through the same binding chain as a value name. NamespaceSymbol::Type(TypeName) binds a name to an identity, never to a resolved type, so it can be named before it is defined.

Identity carries arity

TypeName { module, name, arity } keys on the owning module id, so t in-module and Mod.t from outside are one identity. t/0 and t/1 are not.

Definition is a fact

TypeDefined(TypeName) publishes the resolved Ty from a typed store with a Presence revision. A spec waits on it like any other fact. 

@spec foo(SomeModule.t(float), integer) :: integer

index:   mint ModuleId(SomeModule), TypeName(SomeModule, "t", 1)
         demand DefineModule(SomeModule)              -- reference before define
surface: DeriveTypeDef -> TypeDefined(SomeModule,"t",1) = hard Ty
         DeriveFunctionContract(foo) waits on it -> FunctionContract(foo)

Type denotation is a surface-tier fact: it depends only on indexing and definition, never on activations, return types, or callsite summaries. Every dependency edge runs one way — index, surface, semantic, artifact — so by the time artifact products ask semantic questions, every type name is already a hard Ty. The semantic tier reads types; it never moves a denotation.

Two consequences keep the symbol self-contained and the program minimal. A nominal type carries its own inner: @type Meters :: refines integer mints a Ty whose axes already hold the integer representation, so is_subtype(Meters, integer) reads from structure and no name table is threaded into the lattice. And a protocol domain is a marker, not a union: Enumerable.t depends only on the protocol declaration, while which impls reach the program is decided by demand-driven dispatch as concrete values flow to protocol positions. The implementation relation is closed — "does this type implement it?" has a fixed answer — but the implementers are never enumerated up front: a program that never mentions a Range never pulls the Range impl, and only the callbacks actually called are lowered.

Product Pulls And Artifact Projection

AnalyzeActivation publishes direct-call summaries, reached callee activations, executable needs, a joined return type, and the set of reachable clauses for one rooted activation. Artifact products consume those local facts directly: if a prerequisite is not settled, the producer returns an exact PullWait::Fact; if another artifact is needed, it returns PullWait::Product. 

RootBackendProduct(root)
  waits on RootEntry(root), Recursive(entry), DispatchMask(entry)
  pulls BackendExecutable(entry E)

BackendExecutable(E)
  pulls AbiExecutable(E)

AbiExecutable(E)
  pulls MaterializedExecutable(E)
  pulls ExecutableEffects(E)
  pulls TransportShape(EntryCapture / input / return / resume / boundary positions)

MaterializedExecutable(E)
  waits on ActivationAnalyzed(E.activation), ReturnType(E.activation), CallSiteSummary(...)
  pulls RuntimeDemand(E), OutgoingInputEdges(E), TransportShape(ExecutableReturn(E))

Product materialization clones one executable body, prunes unreachable clauses, rewrites semantically cold local-control entries into explicit halt stubs, and freezes each live callsite to selected symbolic callee executable keys. The root product is only the final dense packaging step; it packages the symbolic executable products already in the request session and does not scan all semantic facts to rediscover membership.

Product freshness is revisioned by exact product generations and exact fact uses. A producer records each dependency at the read site; a wait only names that already-recorded dependency. The scheduler passes one final fact movement per moved key to the pull session by reference; each movement carries the exact state from the scheduler's fact table after propagation, so reconciliation neither relies on transition order nor rescans the world. Outgoing input publication is request-local and order-free: an immutable publisher frontier names requested executables, each publisher owns an immutable map from input slots to source sets, and IncomingInputRelations(root) derives the immutable request-relative relation for the exact current frontier generation. IncomingInputSlot(slot) projects one exact value from that relation. Equal reproduction preserves generations.

Backend-required transport positions wait for produced TransportShape(position) values, not just demanded position membership. Transport shapes are demand-derived. RuntimeDemand(E) settles its demand SCC inside one producer (the ExecutableEffects pattern): the cone is discovered from settled call-edge facts, a bottom-start monotone ascent solves every member together, and only the settled fixpoint is memoized — there is no whole-by-need mid-ascent seed, no consumed-return floor, and no in-flight retraction. A moved transport input retracts only live closures containing that member or registered as readers of that session-product owner. Exact world-fact movement retracts closures registered against that fact. Boundary-publication carrier evidence belongs to the solved closure that produced it, and intrinsic callable callsite mode comes from the authoritative lowered body rather than an optional pruned materialization. Unrelated live closures remain valid. Settled demand retracts only when re-materialization resolves a call edge outside the settlement's callee inventory, which re-keys and re-settles the affected cone. Actual call arguments inherit the selected callee input demand during transport projection, so a recursive caller cannot omit a local argument value that the callee input will decode.

Product Inventory And Fact Taxonomy

The backend handoff is a product inventory, not one giant catch-all structure. Each product owns one narrower question, and each product is derived only from the exact facts and products it names.

MaterializedExecutable

The first backend-owned executable product. It carries one pruned lowered body, selected call edges, return type, per-value types, local transport positions, and frozen extern marshal classes.

AbiExecutable

The ABI projection for one executable. It derives value/param/return reprs, call-edge ABI, explicit return delivery, EntryCapture transport, resume transport, and callable-boundary obligations from materialized and transport products.

BackendExecutable

The symbolic interpreter handoff for one executable. It keeps direct calls as executable keys until root packaging assigns dense indices, so per-executable products stay independent of root inventory order.

RootBackendProduct

The interpreter-ready package. It assigns dense executable indices and callable-entry inventory for the symbolic backend executables already present in the pull session.

NativeProgram

The native-specific handoff above BackendProgram. It carries a Compiler2-owned CPS/codegen-ready projection: direct executable bodies, clause helpers, continuations, callable-constructor metadata, and extern-marshal facts shared native codegen actually consumes, instead of rebuilding ModulePlan, PlannedProgram, or AbiFacts on the side.

Durable Compiler2 artifact facts are:

  • selected call edges
  • return delivery carried by ExecutableNeed
  • extern marshal classes
  • effect summaries
  • callable-boundary obligations
  • settled clause-entry dispatch
  • stable emission inventory
  • backend-ready structured bodies with settled executable targets
  • native-codegen handoff facts derived from BackendProgram

Rejected baggage stays out of Compiler2 facts:

  • SpecPlan as a backend artifact surface
  • SpecRegistry or SpecId as semantic identity
  • old AbiFacts sets such as native_fns, cont_fns, cont_target_fns, and cont_extras_count
  • callable wrapper signatures as compiler facts instead of backend-local lowering details
  • formatted telemetry payloads instead of raw ids, facts, and opaque structures

Interpreter work should consume RootBackendProduct(root), and native work should consume NativeProgram, not invent old planner/codegen state while wiring JIT or AOT. If a backend consumer needs semantic, reachability, or type answers after MaterializedExecutable(E), that missing information belongs as a named fact or product instead of an adapter-side query back into the semantic world.

Native Codegen Contract

NativeProgram(root) is the last Compiler2-owned artifact before JIT and AOT. Shared native codegen is allowed to ask only backend-consumption questions at that rung:

Old shared-native input Compiler2-native answer
prepared Module NativeProgram.module
executable / helper inventory NativeProgram.entry plus NativeProgram.bodies[*].fn_id and origin
ModulePlan.effective_returns and fn_effects NativeBody.return_ty, return_abi, and effects
SpecPlan.vars type queries NativeBody.value_types
PlannedProgram.callable_entries NativeProgram.callable_entries
callable-constructor lookup through planner state NativeBody.callable_constructors
extern decls plus wire classes NativeProgram.module.externs plus NativeBody.extern_marshals
continuation / entry ABI classification NativeBody.entry_abi and NativeBodyOrigin::Continuation
runtime type-membership questions explicit RuntimeTypePredicate facts

Illegal questions after NativeProgram(root):

  • reading ModulePlan, PlannedProgram, SpecPlan, SpecRegistry, or AbiFacts
  • asking reachability, callee-selection, or semantic-closure questions
  • re-deriving callable-entry obligations, return lanes, or extern marshal classes from old-world planner state

Rich semantic Ty facts stay above this seam. Direct runtime tests and cached receive dispatch cross it through RuntimeTypePredicate, the first-class runtime-observable predicate layer shared by compiler2 native codegen, legacy receive dispatch, and the interpreter.

Current conclusion from the code: no missing closed fact has been identified for the current shared native codegen inputs. Compiler2::compile_root_jit, run_root_jit, and compile_root_aot now consume NativeProgram(root) through the shared backend without prepare_preplanned_native. fz2 is the side-by-side outer shell for those front doors. The remaining work above this seam is cutover: switch or retire the old fz surface and remove the fallback plumbing once parity is proven.

Worked Example: Quicksort Plus foo/0

One local design change matters for the next wave of control work: a function body is no longer "a list of steps plus a final result." It is a small entry graph.

  • LoweredClause owns head projections and points at the ControlEntryId where its body starts.
  • LoweredEntry is one reusable local control node: captured inputs, straight-line steps, and one tail.
  • LoweredTail is the only place control can branch, call, or return.
  • ControlDestination says whether a value returns from the executable or is delivered into another local entry.

That sounds abstract, but it removes the old weakness directly. A non-tail call no longer needs hidden "finish the rest of the block" machinery. It simply names the resume entry that receives the result: 

entry N:
  steps...
  tail = DirectCall { ..., dest: Deliver(resume_k) }

entry resume_k:
  origin = CallResume { value: v }
  captures = [...]
  steps...
  tail = ...

Clause bodies use ControlEntryOrigin::Clause. Compiler-made joins and branch arms use Branch. Non-tail calls deliver into CallResume { value }. Local control that moves a value without crossing a callable boundary, like receive arms, delivers into LocalResume { value }. The important part is that backend and native lowering now consume this explicit control graph mechanically instead of trying to recover it later from positional tailness. The backend interpreter preserves the same model: a direct tail call may park on receive, and the blocked task keeps a backend continuation stack so the eventual wake can still deliver back into the caller's resume entry.

01Discovery is cheap

Submit quicksort plus an extra top-level fn foo(), do: 42. The first drive only runs IndexCode. It parses the source, stores the top-level items, and publishes CodeIndexed(code). No functions are defined yet. No bodies are lowered. No activations exist.

02Demanding main/0 scopes only what the root needs

Submit root {GLOBAL, main, 0, Value}. The next drive scopes runtime:runtime.fz, saves the prelude namespace head, scopes the user code, and publishes: 

FunctionDefined(main/0)
FunctionDefined(qsort/1)
FunctionDefined(partition/4)
FunctionDefined(append/2)
FunctionDefined(foo/0)
RootEntry(root)

Still absent: LoweredBody(foo/0), any Activation(... foo ...), and any runtime module surface unrelated to the root.

03The root seed starts the first activation

SeedRoot(root) waits until Recursive(main) and DispatchMask(main) exist, then publishes the entry demand facts: 

Activation(root, main/0, []) = Inputs([])
Executable(root, main/0, [], Value)

The artifact path does not rely on self-scheduled follow-up work. When the interpreter asks for RootBackendProduct(root), the product driver waits on the exact facts needed to key the entry executable and then pulls BackendExecutable(main/0[]).

04Activation analysis co-derives types and plans

AnalyzeActivation(root, main/0, []) lowers nothing new beyond main/0's own body and follows only dispatch-reachable clauses. It publishes one direct-call summary: 

CallSiteSummary(root, main, qsort_call) =
  { callee: qsort/1,
    input_types: [nonempty_list(int)],
    need: Value,
    return_ty: list(int) }

That same job also contributes: 

Activation(root, qsort/1, [nonempty_list(int)])
Executable(root, qsort/1, [nonempty_list(int)], Value)
ReturnType(root, main/0, []) = list(int)
ActivationAnalyzed(root, main/0, [])

05Recursive inputs settle by joined activation facts

Later analyses of qsort/1, partition/4, and append/2 may re-contribute to an existing activation with different but compatible input types. Those contributions join in the Activation slot: 

Activation(root, qsort/1, [nonempty_list(int)])   -- first contribution
Activation(root, qsort/1, [list(int)])             -- later recursive contribution
join => Inputs([list(int)]) after refine_widen + alpha normalization

There is no second type-fixpoint loop hiding behind this. The joined activation fact is the loop.

06Tuple-field need rides on the same callsite fact

The call from qsort/1 to partition/4 needs tuple-field projection, so its summary carries that need directly: 

CallSiteSummary(root, qsort, partition_call) =
  { callee: partition/4,
    input_types: [list(int), int, list(int), list(int)],
    need: TupleFields(2),
    return_ty: tuple([list(int), list(int)]) }

There is no separate ReturnNeed fact to keep in sync.

07Product demand excludes foo/0

When RootBackendProduct(root) pulls the entry backend executable, products follow only the symbolic call edges recorded by demanded executable products: 

RootBackendProduct(root)
  entry: main/0[]
  products: BackendExecutable(main), BackendExecutable(qsort), BackendExecutable(partition),
            BackendExecutable(append), ...runtime helpers named by call edges...

foo/0 is absent because no reached callsite ever referenced it, so no product key asks for its body or backend executable.

08Products freeze and package only demanded executables

MaterializedExecutable(E) clones one body, prunes unreachable clauses, rewrites semantically cold local-control entries into explicit halt stubs, and records symbolic call edges. AbiExecutable(E) then makes return delivery, ABI lanes, EntryCapture positions, resumes, and callable entries explicit without asking new semantic questions. BackendExecutable(E) lowers one symbolic body. Finally, RootBackendProduct(root) assigns dense indices and packages the request-local inventory into BackendProgram. Redefining uncalled foo/0 later does not change that root product. Redefining main/0 can, because the settled local callsite summaries it depends on may change.

Worked Example: Enum.reduce

01Prelude scope is enough to name runtime APIs

A user function can call Enum.reduce/3 with no eager runtime parse at construction time. The first demanded scope pulls runtime.fz, binds the prelude namespace, and lets user source resolve Enum as a module id.

02The root only warms the reached runtime surfaces

When main/0 calls Enum.reduce/3, AnalyzeActivation(root, main/0, []) publishes: 

CallSiteSummary(root, main, enum_reduce_call) =
  { callee: Enum.reduce/3,
    input_types: [list(int), int, reducer_closure],
    need: Value,
    return_ty: int }

That summary contributes a rooted activation for Enum.reduce/3. Only then does the engine submit and define the runtime module surface that owns that function.

03Protocol dispatch is still ordinary fact work

The runtime implementation can call the protocol callback Enumerable.reduce/3, which then resolves to the concrete Enumerable.List.reduce/3 implementation because the receiver type is a list. Each hop publishes one whole callsite summary and one callee activation: 

CallSiteSummary(root, Enum.reduce, protocol_call) = Enumerable.reduce/3
CallSiteSummary(root, Enumerable.reduce, impl_call) = Enumerable.List.reduce/3
Activation(root, Enumerable.List.reduce/3, [...])

04User closures become ordinary generated functions

The reducer lambda is lowered into a generated function id owned by the enclosing user function. Its activation and return type live in the same fact families as named functions: 

FunctionDefined(lambda#reduce_sum/2)
LoweredBody(lambda#reduce_sum/2)
Activation(root, lambda#reduce_sum/2, [int, int])
ReturnType(root, lambda#reduce_sum/2, [int, int]) = int

05Unreached runtime code stays cold

The final root product contains only the user function, the reducer lambda, and the reached runtime/protocol helpers. Unrelated runtime modules such as Utf8 or unreached Enum helpers never get product keys and therefore never reach materialization.

Observability And Guideposts

Telemetry carries raw ids, facts, and opaque structures. Formatting belongs in handlers. The compiler surface emits spans for drive and each job, plus state-defining events such as function.defined, callsite.defined, backend_program.defined, native_program.defined, and pull.session.finished. Tests observe those events instead of poking through world internals.

Summary tests

src/compiler2/drive_test.rs is the fast contract surface. The quicksort, Enum.reduce, and variadic-extern tests assert finite closure size, exact reached callsites, absence of cold helpers, and the pulled backend/native products.

Useful rerun: cargo test --lib compiler2_ -- --nocapture

Deep trace

src/compiler2/telemetry_dump_test.rs is an ignored one-off harness that writes the full quicksort event stream to /tmp/fz-compiler2-quicksort.jsonl through a JSONL handler. The handler does any debug formatting; emit sites do not.

Useful rerun: cargo test --lib compiler2::telemetry_dump_test::dump_quicksort_compiler2_telemetry_to_jsonl -- --ignored --exact --nocapture

What to watch

The important numbers are not raw event counts in isolation. They are: which jobs were coalesced, which facts changed revision, which waits remained unresolved, and which roots reclosed after a redefinition.

North Star Checklist

  • Stable ids before meaning: modules and MFAs can be referenced before they are defined.
  • One local type world: Ty is compiler-owned and never compared across worlds.
  • Represent, don't name: Types carries no naming duty; a type name is an identity defined by TypeDefined, settled at the surface tier before any semantic question is asked.
  • One logical fact, one key: whole callsite summaries replace split partial facts.
  • No separate type loop: activation-input joins are ordinary fact replacement.
  • Lazy runtime bootstrap: runtime.fz and runtime modules warm only when demanded.
  • Product-keyed artifacts: artifact producers return exact fact/product waits; they do not self-schedule follow-up work.
  • Artifact isolation: materialization consumes settled local facts and named products, then final root packaging only densifies request-local inventory.
  • Blast radius by revision: redefinition propagates only as far as fact revisions actually change.

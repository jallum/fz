1. A macro is a function that returns code

An ordinary function receives values and returns a value. A macro receives unevaluated code — the caller's argument, as written, not as run — and returns code too. The compiler splices what the macro returns into the call site, then keeps compiling.

That's the whole idea. Everything else in this guide is about writing the code a macro returns, and one rule that keeps a macro's own bookkeeping from leaking into the program that calls it.

2. quote and unquote

quote turns the code inside it into data instead of running it:

quote do
  1 + 2
end

This does not evaluate to 3. It evaluates to a small tree describing the call 1 + 2 — the same shape a macro receives its arguments in, and the same shape a macro is expected to return.

unquote(e) is the escape hatch: inside a quote, it splices in the value of e, evaluated right where it's written, instead of quoting e itself:

defmacro emit(x) do
  quote do: unquote(x) + 1
end

emit(7)  # expands to `7 + 1`, runs, returns 8
Mental model: a quoted block is a little AST value you can build, inspect, and hand back. unquote is the one place inside a quote where you drop back into "evaluate this now" instead of "quote this."

3. defmacro, step by step

defmacro unless_(cond, do_block) do
  quote do
    if unquote(cond), do: nil, else: unquote(do_block)
  end
end

Walking through a call unless_(ready, do_the_thing()):

  1. The compiler sees a call to unless_/2 and finds it is a macro, not an ordinary function.
  2. cond and do_block are bound to the unevaluated arguments — quoted code for ready and quoted code for do_the_thing(), neither has run yet.
  3. The macro body runs, at compile time, and returns a quoted if expression built from those two pieces.
  4. The compiler splices that returned tree in place of the call, then keeps compiling — the if now lowers and runs like any if a person typed directly.

A macro may also just return a literal — a number, an atom, a string, or a small tuple — instead of a quote block. Both work; quote do: 42 and a bare 42 mean the same thing.

A macro call can take a trailing do ... end block the same way if or case can, with an else section if it needs one. The block arrives as one extra argument, a [do: ..., else: ...] keyword list, unevaluated like every other macro argument:

defmacro pick(flag, [do: then_branch, else: else_branch]) do
  quote do
    if unquote(flag), do: unquote(then_branch), else: unquote(else_branch)
  end
end

pick(ready) do
  "go"
else
  "wait"
end

4. Hygiene: a macro's variables are its own

Suppose a macro's own quoted body assigns a variable:

defmacro set_local() do
  quote do: t = 99
end

def main() do
  t = 1
  set_local()
  t  # 1, not 99
end

Even though the macro's expansion textually reads t = 99 and gets spliced into main, it does not touch main's own t. The macro's t and the caller's t are different variables that happen to be spelled the same way. This is hygiene, and fz gives it to you automatically — you don't have to gensym anything yourself.

Hygiene runs both directions. A macro cannot see the caller's variables either:

defmacro read_t() do
  quote do: t
end

def main() do
  t = 5
  read_t()  # diagnostic: lower/unbound — the macro's own `t` was never bound
end

The macro's t is a variable belonging to read_t, not to main, and read_t never assigns it. Reaching for a name nobody bound is exactly as much an error inside a macro's own quote as it would be anywhere else.

Hygiene is also per call, not per macro. Two calls to the same macro never share a binding:

defmacro double_via_temp(x) do
  quote do
    t = unquote(x)
    t + t
  end
end

double_via_temp(21)  # 42 — both occurrences of the macro's own t, in ONE expansion, are the same binding

and

defmacro step(write) do
  if write do
    quote do: t = 1
  else
    quote do: t
  end
end

step(true)
step(false)  # diagnostic: lower/unbound — this call's own t was never bound, even though the FIRST call's t was

5. How fz tells two same-named variables apart

A variable's real identity is its spelling plus where it was written, not its spelling alone. A variable written by hand is User. A variable written inside a macro's own quote carries that macro, plus a number saying which of that macro's calls produced it. So t the caller wrote and t the macro's quote wrote are never the same binding, no matter how many times the macro runs.

This is the same idea Elixir uses under the name context: a variable is {name, context}, and only variables with an identical pair ever resolve to the same binding.

6. var! — reaching into the caller on purpose

Sometimes a macro wants to bind or read the caller's own variable — an assertion helper that has to define a name the caller goes on to use, for example. Wrapping a variable in var!(...) inside a quote tells fz "treat this one as if the caller had written it by hand," opting that one variable out of hygiene:

defmacro bump_and_shadow() do
  quote do
    t = 1
    var!(t) = var!(t) + 1
    {var!(t), t}
  end
end

def main() do
  t = 9
  bump_and_shadow()  # {10, 1}
end

Inside bump_and_shadow's own quote, the bare t is still the macro's own hygienic variable, isolated at 1. Every var!(t) is a different variable — the caller's t — so it reads 9, becomes 10, and that 10 is what the caller sees afterward.

7. __CALLER__ and __ENV__

A macro that needs to know something about where it's being called from can ask for __CALLER__, a small map with the calling module, function, and namespace. __ENV__ is the same shape, but for where the macro itself was defined — useful for a macro that wants to refer back to its own defining module.

Neither of these is a hygiene escape hatch on its own — they hand back data about a scope, not a way to read or write that scope's variables. Use var! for that.

8. Footguns

A macro cannot read a caller's variable by spelling alone. If your macro's quote reads a name it never bound, that's an unbound variable, full stop — hygiene does not fall back to "check the caller's scope." Reach for var! when you actually want that.
var! opts a name out of hygiene entirely, not just for one read. Every occurrence of var!(name) for the same spelling, anywhere in the expansion, is the caller's ordinary variable. Don't reach for it just to silence an unbound-variable diagnostic; use it when the macro's whole point is to bind or read something in the caller's scope.

9. The contract

A macro's own variables never collide with the caller's, and never collide between two different calls to the same macro — unless you say var!, in which case you get exactly the caller's variable, on purpose.

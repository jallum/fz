1. Values — any value refs and container storage

fz has one dynamic value abstraction: AnyValueRef. It is one opaque word. Its tag says what kind of value it names, and its address points at the payload. Known typed lanes still carry raw i64 or f64 when the type is known; boxing into an any value ref is the last resort for any boundaries such as send, dynamic container reads, and generic runtime calls.

The storage shape is chosen by where the value lives:

  • AnyValueRef: one opaque word used at dynamic boundaries. Its high tag bits say whether the address points at an int, float, atom payload, list, map, tuple/struct, closure, binary, or resource. It may survive allocation, yield, or GC only when stored in a traced root owner such as the mailbox or a parked receive record.
  • Container-local typed storage: used inside lists, maps, tuples, and closures. Containers store compact payload words and the minimal kind metadata their layout needs. This is private object layout, not a second value abstraction.

Heap objects are 16-byte aligned, so the low 4 bits of any real heap address are clear. The only use of those bits is the GC's forwarding marker. AnyValueRef words, and every heap-object word that names another object, carry the logical kind in architecture-owned high bits and must only be inspected through the AnyValueRef API.

AnyValueRef uses the runtime ValueKind tag values: 0 Null, 1 List, 2 Map, 3 Struct, 4 Closure, 5 Bitstring, 6 ProcBin, 7 Resource, 13 Int, 14 Float, and 15 Atom. The empty list is a null-address List ref. The tag lives at bit 56 on arm64/TBI and bit 57 on x86_64; callers use the API rather than those bit positions directly.

The canonical object-local kind table is below. Heap objects use these values for compact metadata. Generated code and runtime helpers project to or from AnyValueRef through typed APIs; persistent dynamic values are not carried as public word-plus-kind pairs.

A value ref is a stamped envelope. At dynamic boundaries the stamp is on the envelope itself. Inside containers, the envelope can be packed more tightly because the container layout already says where the stamp lives.

A few consequences of this layout:

  • The low nibble of a live pointer is zero. Heap objects are 16-byte aligned. Heap tags 0x1 through 0x7 identify the object kind in the high bits; masking them off recovers the address, and the low nibble is never part of either.
  • Integers and floats are raw in typed storage. A local tag 0xD means the payload is a full signed i64. A local tag 0xE means the payload is raw f64::to_bits().
  • Specials are atoms. nil, true, and false are reserved atom IDs. Empty list has a dedicated AnyValueRef tag at dynamic boundaries; inside list links it is represented by the empty-list sentinel used by that layout.

The GC follows heap-kind tags 0x1 through 0x7. Immediate side-band tags pass through unchanged. When Cheney relocates an object, it overwrites one marker word of the from-space copy with to_space_address | 1; later scans read that word and treat any set low nibble as "already forwarded". The marker word is word 1 (the link) of a list cons and word 0 of every other kind, and each kind lays that word out so a live value has a clear low nibble: a struct, closure, bitstring or map header keeps four clear bits below its fields, and a ProcBin or Resource keeps a 16-aligned pointer there. One read decides; no second word is consulted.

Objects the program carries in read-only data (static structs, static closures, halt continuations and the nil slot) are never on a heap. Every reference to one has a single literal bit set in its address word, above the kind field and at the same position in a ref word, a field or capture payload, a map entry, a list head and a list link. The collector and deep copy read that bit: a tagged reference is left in place or shared, an untagged one is a heap pointer and is copied. Nothing walks the heap's block list to decide. Debug builds cross-check the bit against the block ranges and assert that an untagged pointer lies in from-space and a tagged one does not.

Old per-float heap objects are retired. Floats in typed code travel as native f64; floats stored in containers are raw bits. A boxed scalar is allocated only when an any boundary needs a AnyValueRef.

Container-local layouts

Generic containers store raw 64-bit payload words and keep compact kind metadata beside those payloads. The canonical tag values above are shared by heap pointer tags and container-local metadata.

List cons cell:

  offset 0:  head: u64
  offset 8:  link: u64
             high metadata = alias flag + head kind tag
             address bits  = next cons address, or 0 for end-of-list
             low 4 bits    = clear pointer-alignment bits

The cell itself is named by a TAG_LIST pointer. Empty list is the null next address. Improper-list representation is outside this first layout migration and must be handled by a follow-up if encountered. The alias flag is a conservative reuse guard: runtime helpers may mark a cons aliased. Compiler-facing reuse helpers treat an aliased source cell as an allocation miss: unaliased cells may be relinked in place, while aliased cells use fallback allocation to produce a fresh cons with the same head and the requested tail.

Map:

  offset 0:                      count: u64
  offset 8:                      tag_bytes: [u8; N], padded to 8-byte alignment
  offset 8 + pad(N, 8):          keys:   [u64; N]
  offset 8 + pad(N, 8) + 8N:     values: [u64; N]

Each map entry has one tag byte: high nibble = key kind, low nibble = value kind. Total size is 8 + ceil(N/8) * 8 + 16N, then rounded to the next 16-byte boundary.

Dynamic roots:

  AnyValueRef    // one word; tag + address

Mailboxes, parked selective receive pins, matcher inputs, matcher outputs, and scheduler handoff values use AnyValueRef. Heap-object refs point at heap objects and are traced by object layout. Scalar refs point at boxed scalar payloads and have no children. Sentinels have no children.

There is deliberately no generic persistent word-plus-kind carrier. Anything that survives scheduler or GC boundaries is either a AnyValueRef root or an ordinary heap object reached from one. Container-local metadata is private to the object layout.

Destination planning:

Destination planning lets the compiler decide where a value should be built or delivered before it starts building it. Destination passing is the lower-level mechanism used when that plan has to carry an unpublished construction location or hidden call context through IR or native ABI. The destination is private process-local construction state. Once it is frozen or returned to user code, the result is an ordinary immutable value.

For tuple-shaped results, the compiler can avoid a temporary tuple when the caller immediately projects the fields:

  {lo, hi} = partition(p, rest, [], [])

The selected native path can deliver lo and hi directly to the continuation as independent values. No published tuple is mutated, and no tuple object has to exist just to be projected.

For recursive list code, the compiler can pass the final tail as context and allocate immutable cons cells in front of it:

  append(qsort(lo), [p | qsort(hi)])

That shape can be executed as:

  hi_tail    = qsort_into(hi, outer_tail)
  pivot_tail = [p | hi_tail]
  qsort_into(lo, pivot_tail)

The cons cells are still ordinary immutable list cells on the process heap. The compiler only chooses their tail before building the prefix.

Source-level structural helpers do not need to become BIFs just to be predictable. A plain recursive append:

  def append([], ys), do: ys
  def append([h | t], ys), do: [h | append(t, ys)]

still compiles as source code. In the append fixture, append([1, 2, 3], [4, 5]) allocates the five list-literal cons cells and no prefix-copy cons cells, with no tuple/struct or map allocation in the value path. Each recursive append construction retains its exact source cell; there is no append BIF.

Map construction:

Maps are immutable values. A map literal or update is lowered through an unpublished process-local destination, linear put operations, and a freeze that publishes the immutable map:

  dest = fz_map_dest_begin(extra=2)        // unpublished storage
  _    = fz_map_dest_put_parts(dest, k0, v0)
  _    = fz_map_dest_put_ref(dest, k1, v1)
  out  = fz_map_dest_freeze(dest)          // immutable canonical map

The destination lives on the owning process heap and is not visible as a published value. Freeze sorts by runtime map ordering, removes overwritten duplicate keys, and returns the canonical immutable map. Known key/value representations use fz_map_dest_put_parts; unknown refs use fz_map_dest_put_ref. Dynamic map reads still return AnyValueRefs when the caller needs an any.

Return-demand destinations:

Some destinations are selected at call boundaries instead of local literal sites. The planner records these as ReturnDemand capabilities on the selected SpecKey. TupleFields delivers a tuple result as independent continuation values; a tail-call edge can instead forward the caller's own demand. Recursive list code needs no list-tail delivery shape: it builds the list forward with an O(1) continuation (tail recursion modulo cons) plus list-retention transport. Codegen implements the planner-selected capability; it does not guess from source names.

For recursive list code this is tail recursion modulo cons: the compiler passes the tail context explicitly, then allocates immutable cons cells in front of that tail. In fixtures/quicksort, the native paths pin list_cons_allocs = 11, list_cons_bytes = 176, struct_allocs = 0, and headline heap bytes 176.

Other heap layouts:

  • Struct: offset 0 schema_id: u32, flags: u32; offset 8 typed fields declared by the schema; total size is align16(8 + schema payload).
  • Closure: offset 0 schema_id: u32, flags: u32; offset 8 fn_ptr: u64; offset 16 raw capture words; capture kind bytes follow the raw words and are padded to 8-byte alignment.
  • Bitstring: offset 0 bit_len: u64; offset 8 bytes, padded to 16-byte alignment.
  • ProcBin: offset 0 shared_ptr; offset 8 mso_next; offset 16 byte_offset; 32 bytes total.
  • Resource: offset 0 resource_ptr; offset 8 resource discriminator; offset 16 destructor closure payload; offset 24 destructor closure kind byte plus padding; offset 32 mso_next; 48 bytes total.

2. The process heap — bump allocation

Every fz process has its own private heap. No sharing, no locks. Allocating is a pointer bump — two comparisons and an increment on the fast path.

  Process heap (one block, contiguous):

  block_start                                             block_end
      │                                                       │
      ▼                                                       ▼
      ┌───────────────────────────────────────────────────────┐
      │ allocated objects ← bump_top                          │
      └───────────────────────────────────────────────────────┘
                            ▲
                         bump_top
Think of the heap as a stack of paper. To "allocate," you write your object on top and move a finger (the bump pointer) down by however many lines you used. Nothing else needs to happen on the fast path.

Heap objects are 16-byte aligned, but they no longer share a universal 16-byte header. The low 4 bits of the pointer identify the heap kind, and each kind has its own prefix and size function.

Per-kind layouts:

closure, n capturesalign16(16 + n×8 + align8(n))raw captures + one kind byte per capture

Resource48 bytesshared ptr + discriminator + destructor closure + mso_next

Ordinary large objects — tuples with many fields and maps with many entries — live on the process heap and grow into bigger blocks as needed. Bitstrings above SHARED_BIN_THRESHOLD_BYTES (64 bytes) don't live on the process heap. Instead the heap carries a 16-byte ProcBin stub that points into the shared zone.

Block pool and block capacities

Blocks come from a per-thread pool sized by a Fibonacci-then-geometric size table (1 KiB up to ~7 MiB); a heap's tip starts at the first entry and climbs the table. When a block fills before GC fires, a new block one step up becomes the tip and the old one joins blocks, recorded with its fill and capacity. An object larger than that step is not made the tip: it gets a block sized for it, parked on blocks straight away, and the tip keeps filling. All parked blocks are reclaimed at the next GC.

The table has neither a floor nor a ceiling on what a block may be. A request below the first entry or above the last gets a block of exactly its size (rounded up to 16 bytes); that block comes from the system allocator, not the pool, and goes back to it when it is released. An object larger than the last entry is copied like any other when the collection that reaches it releases the block.

The gift window

A heap can lend its allocation path to a copy whose result belongs to another heap. Cross-process send is its user: the sender copies a message, or a match's bound values, inside one, and the segment waits on the receiver's in_queue until the receiver's next dispatch grafts it.

The sender measures first. measure_deep_copy walks the value set the way the copy will and returns the bytes it will allocate, counting shared structure once. Heap::begin_gift takes that figure, sets the current tip aside and installs one block of the smallest capacity that holds it (an exact block when it is below or above the table, so a 16-byte message occupies a 16-byte block). The copy runs through the ordinary bump path and fills the block without overflowing it. Heap::end_gift asserts the block's fill is exactly the measured bytes, turns the block into a GiftSegment and puts the saved tip back with its free space intact. The segment carries that one block (with its fill), the prefix of the MSO chain that the window produced, and the number of objects allocated. The heap's allocation statistics stay with it, its live_count goes back to what it was. A collection cannot run while a window is open.

The receiving heap calls Heap::graft: the segment's block joins its blocks, its MSO prefix is spliced ahead of the receiver's chain. Every parked block counts toward bytes_used by fill, never by capacity, so a kilobyte block holding one cons cell is sixteen bytes of bytes_used. The same fill raises live_baseline: a gift is packed and fully live, so it is survivor data and never allocation pressure. A segment that is dropped without being grafted releases its block and every stub's off-heap reference.

The MSO chain

Each heap carries an intrusive linked list of every ProcBin and Resource it owns. The head pointer lives on the heap (mso_head); the "next" link lives inside each stub: ProcBin uses offset +8, Resource uses offset +32. "MSO" is the historical BEAM name — "Mixed Set / Off-heap" — for the list of objects whose real bytes live elsewhere.

The MSO chain is a "things to clean up later" list. Every time the heap makes a ProcBin or Resource, it adds the stub to the chain. After each GC, we walk the chain to figure out which stubs survived and which need to release their off-heap payload. See §9 for the details.

3. Reductions, collection timing, and boundary GC

Processes run on a reduction budget. Every compiled or interpreted loop back-edge spends budget. When the budget reaches zero, the process materializes a scheduler-owned continuation closure and yields. Collection timing is separate: allocation makes the heap due for GC, but it does not spend reductions and does not force a yield.

should_gc

Every Heap::alloc() call is a bump and nothing else. Whether a collection is due is a question about the heap's state, answered by Heap::should_gc when the scheduler asks at a boundary: the tip's fill plus the fill of every parked block, less the heap's live_baseline, against the larger of that baseline and half the smallest tip. The baseline is the bytes known to be live: a collection sets it to the bytes that survived, graft raises it by the gift's fill, and allocation leaves it alone. A heap holding N live bytes is therefore due a collection once it has allocated N more. A collection that reclaims those bytes answers the question by itself; nothing is cleared. If an allocation no longer fits in the current block, the heap parks it in blocks for the next Cheney pass and installs a tip one step up, unless the object is larger than that step: then the object gets a parked block of its own and the tip stays.

  bump_top += size
  if bump_top would cross block_end {
      if size > next_block_capacity(block_size) {
          blocks.push(block sized for the object)   // tip unchanged
      } else {
          blocks.push(tip); tip = block one step up
      }
  }

  should_gc = bytes_used - live_baseline >= max(live_baseline, SIZE_TABLE[0] / 2)

Compiled yield telemetry still samples the margin before and after the reduction-yield slow path, so max_yield_continuation_bytes includes the continuation closure, scalar boxes, and materialized continuation state observed while yielding.

The back-edge check

Every loop in fz is a tail-recursive call. The compiler uses Tarjan SCC (already run by the type system) to figure out which tail calls are back-edges: a call whose callee is in the same strongly-connected component as the caller. Self-recursion is the easy case; mutual recursion (f → g → f) is covered automatically.

At every back-edge call site, codegen emits:

  gv        = global_value.i64 %FZ_REDUCTIONS_REMAINING
  remaining = load.i32 gv+0
  remaining = remaining - 1
  store remaining, gv+0
  brgt remaining, 0, $fast

  ; slow path (budget exhausted):
  call fz_yield_slow_path_begin()
  cont = call fz_alloc_closure(next_loop_fn, argc, halt_kind, code_ptr)
  store arg0, cont.capture[0]
  store arg1, cont.capture[1]
  ...
  call fz_yield_mid_flight_report(cont, remaining, YIELD_REASON_REDUCTIONS)
  return [YIELD_PTR]                          ; sentinel; scheduler sees it and re-queues

  $fast:
  return_call loop_fn(args...)                ; unchanged hot path

The slow path only fires when the process has spent its quantum. Nothing else makes a process yield: a heap that is due for collection waits for the process to reach a boundary.

4. Park-time GC — Cheney with explicit roots

When a process parks on receive, all live data is reachable from the roots the process holds: mailbox values, the park record's outcome closure templates, after body and pinned values, and the runnable continuation closure. No stack scan, no register enumeration.

  from-space (current block + parked blocks)
  ┌────────────────────────────────┐
  │ [dead]  [dead]  [live]  [dead]  │
  │      scheduler roots point ──►│──►closures + AnyValueRefs
  └────────────────────────────────┘
           │ Cheney BFS copy │
           ▼
  to-space (a fresh tip; copies park blocks as it fills)
  ┌─────────────────┐
  │ [live][live][live]│
  │         bump_top│
  └─────────────────┘
  from-space → pool (freed)
Cheney is the world's tidiest move-out. You bring a fresh empty room (a fresh tip). Starting from one pointer, you copy every live object across. Once you're done, you walk out and burn the old room. Nothing dead gets a ride.

The accepted consequence: a receiver that consumed a lot of mail keeps the dead blocks, once the mail is dropped, until its own allocation reaches the baseline the gifts raised. A process that receives a large gift, drops it and then goes quiet holds that memory; shrinking an idle heap is a separate policy, for which the census would have to show a need.

To-space is a chain

A copy is placed by the same bump path as an allocation. The collector installs a fresh tip and every copied object goes through Heap::bump: when the tip is full it is parked on blocks and a tip one capacity step up is installed, and an object larger than that step is parked alone in a block of its own with the tip untouched. The scan pops a worklist of copied objects rather than walking an address, so to-space needs no contiguity: it is the new tip plus the parked blocks.

The tip's capacity has one job, how far the bump pointer runs before a block is parked, and one rule, climb the table on overflow. The fresh tip's capacity is only a starting point: pick_block_capacity(live_baseline), the last survivors plus any grafted gifts (the smallest tip when the baseline is empty). A heap whose live set is steady collects into one block; a guess that is too small costs the extra blocks the copy parks, and the next collection's guess is the bytes this one copied. A gift is one parked block like any other, so its fill is part of the bytes in use. After the pass the old tip and every parked block go back to the pool, or to the system allocator when exact, with the rest of from-space.

After the BFS scan, live_baseline is the sum of the sizes of the objects copied. That feeds the next GC's trigger and tip guess, and is the live_bytes of the pass's GcStats.

Each copied from-space object gets an in-band forwarding marker written into its marker word: to_space_address | 1. Any other pointer to the same object reads that marker, strips the low nibble, and is rewritten to the same-kind to-space pointer. This is how shared structure stays shared after collection without side tables.

5. Mid-flight GC — collecting a running loop

When the back-edge slow path fires, the process is mid-loop. The compiler turns the in-flight state into the same shape the scheduler already knows how to run: a zero-arg closure. The closure's captures are the loop args being passed to the next iteration, plus the current continuation.

  struct Process {
    ...
    runnable_closure:      *mut u8,       // tagged closure to run next; null = none
    reduction_yields:      u64,           // ordinary budget exhaustion
  }

Closure captures use the regular container-local layout: raw payload words plus compact kind bytes stored inside the closure object. There is no fixed argument limit, no side table, and no separate GC storage. The GC roots the closure, follows its captures, and forwards anything reachable. Resuming is just running the closure.

A back-edge yield is like a relay runner setting their baton down in a labelled box before stepping aside. The collector tidies the track; the next runner picks up the baton from the box and keeps running.

Continuation closure

For each back-edge callee shape, codegen emits a small closure entry alongside the function body:

  fz_mid_flight_cont_fn42(self):       ; SystemV, scheduler-callable
    return fz_mid_flight_cont_fn42_tail(self)

  fz_mid_flight_cont_fn42_tail(self):  ; Tail-CC
    r0 = load_capture(self, 0)
    r1 = load_capture(self, 1)
    ...
    return_call fn42_body(r0, r1, ...)

The SystemV entry lets the Rust scheduler call the closure through the normal fz_resume path. The Tail-CC sibling reloads captures into the callee's native ABI and tail-calls the loop body.

6. GC roots and the MSO sweep

The GC traces only explicit roots. Everything else is dead.

One method, Process::collect, builds the root set from the process and calls the one collection entry, Heap::collect. Every scheduler reaches the same root set, and each slot holds its forwarded value when the call returns.

The roots of a process
runnable — a zero-arg closure capturing the next loop state. It is traced through the normal closure layout.

The park record — the receive's clause-body closures, its after body, and its pinned values (heap values the matcher compares against). The matcher reads the pinned values whenever a message arrives, so they move with everything else. Every parked receive carries a compiled matcher; the catch-all form receive do msg -> msg end is the accept-any shape.

process.mailbox — every message is an AnyValueRef. Heap-object refs are forwarded in place. Scalar refs are scalar boxes: the box is copied, but the payload is not followed as a child edge. This matters for self-send: a process can send itself a message and keep running; that message lives only in the mailbox and would otherwise be collected.

Transient values — whatever the caller holds across the call.

Gifts waiting in the delivery in-queue are not roots. Their blocks join the heap only when drain_in_queue grafts them, and every reference in a gift points into its own segment. Process::collect holds the delivery lock for the whole pass, so a sender cannot probe the park record while it moves.

The interpreter keeps a parked receive's environment and continuations in its own structures. It passes their heap refs to Process::collect as transient roots and writes the forwarded refs back.

MSO sweep — keeping shared-zone refcounts honest

After Cheney's BFS scan completes and before from-space is freed, the GC walks the heap's MSO chain once. Each entry is a ProcBin or Resource stub that was in from-space. The forwarding marker Cheney writes into the first word of every copied object is the entire liveness signal — no separate bookkeeping. One function, procbin::mso_sweep, decides every stub, after a collection and when a process exits (an exit is the same walk with nothing live):

  cur = heap.mso_head
  new_head = null
  while cur != null:
      kind = kind_of(cur)             // ProcBin or Resource from the link's high bits
      marker = read u64 at addr_of(cur)+0
      if low4(marker) != 0:
          next = read_mso_next(kind, cur)       // from-space link survives
          new_addr = strip_low4(marker)         // to-space copy
          link (new_addr, kind) into new_head   // survived; rejoin the chain
      else:
          next = read_mso_next(kind, cur)
          release_payload(kind, cur)             // dead MSO stub; drop its ref;
                                                // a Resource's last ref queues (closure, payload)
      cur = next
  heap.mso_head = new_head

The sweep is O(number of MSO stubs on this heap), not O(heap size). This pass runs in every collection.

A dead Resource's destructor is fz code, so it never runs inside the sweep. Its closure lives in the from-space that is about to be released, so before the sweep the collector forwards the closure of every unreached, unclaimed Resource stub, along with whatever the closure captures. The sweep then queues (closure, payload) on heap.pending_dtors for the resource whose last reference it dropped. A stub that a forwarded closure captures is reached by that, so it survives until a later collection. A process that halts takes the same sweep without a collection: Heap::release_resources_at_exit decides every stub on the chain with nothing live and copies nothing. Heap::drop releases only what a process still holds when the program tears it down without having exited, such as one parked on a receive; no destructor closure runs for those.

7. Scheduler dispatch

Dispatch order

  1. resume the runnable closure
  2. sched_core::end_quantum(scheduler, process):
       boundary = yield (runnable), park (blocked on a receive) or exit
       if heap.should_gc:
         process.collect()          (the JIT emits fz.runtime.gc)
       clear yield reasons
       exit: mark Exited; release the MSO chain with nothing live
       run each queued resource destructor as fz code, oldest first
  3. Requeue: re-enqueue.  Parked: wait for a send or the timer.  Exited: done.

  (The JIT, AOT and interpreter schedulers all run step 2 after every quantum,
  in every state. The interpreter never yields, so it reaches it at a park or
  an exit.)

8. Message passing — copy, self-send, share

Cross-process send

send is an any boundary. The caller passes a AnyValueRef. If the caller only has a known raw scalar, it boxes that scalar first; if it already has a heap-object ref, it passes the ref as is.

When sender and receiver are different processes, the sender does all the work and never writes into the receiver's heap. sched::probe_sender tests the message against the receiver's parked matcher, if it has one, with the sender as the allocating process. It then opens a gift window on its own heap and deep-copies what the receiver will keep: the values the winning clause bound on a hit, the whole message on a miss. A hit that binds nothing opens no window and gifts an empty segment. Heap objects are copied by layout, a list spine cell by cell; scalar boxes are copied as scalar boxes and are not scanned as child pointers. The segment is queued on the receiver's in_queue with its payload, and a hit makes the receiver runnable.

The receiver grafts every queued segment as the first act of its next dispatch, before any of its code or a collection runs. A miss payload joins the mailbox, which process-root GC traces directly; the hit payload finishes the receive, building the outcome closure on the receiver's own heap over the gifted bound values. A receiver whose receive is already matched is not probed again, so there is at most one match in its queue. A receiver that exits with gifts still queued drops them: each un-grafted segment returns its block to the pool and releases its stubs' references.

Self-send (same process)

A process sending to itself pushes the AnyValueRef it already holds onto its own mailbox (sched::self_send). Nothing is copied and the runtime publishes nothing: the sender is running, so it cannot be parked, and the push is the whole delivery. Since process-root GC roots the mailbox, the value survives any subsequent back-edge GC even if the sending code no longer holds a local reference to it.

The mailbox is now a second holder of the same cells, and the in-place list rewrite guard must see them as aliased. The compiler owns that: when the continuation after a call retains a name that may alias an argument, construct_call_ownership (src/compiler2/jobs/body.rs) marks the argument Share, and the Share mode publishes the list spine before the call on every path. A self-sent list the sender can still reach is therefore already published when it enters the mailbox, and a later rewrite of one of its cells allocates a fresh cell instead.

ProcBin — bytes are shared, not copied

When deep_copy_any_value_ref reaches a ProcBin (a stub pointing into the shared zone), it does not copy the bytes. Instead:

  shared_bin_retain(src.shared_ptr)        // atomic ++ on refcount
  dst_proc_bin = dst_heap.alloc_procbin(src.shared_ptr, src.byte_offset)
  forwarding[src] = dst_proc_bin

The gift gets a fresh 32-byte ProcBin viewing the same suffix of the same SharedBin, and the receiver's heap adopts it with the segment. The SharedBin's refcount is now one higher. The bytes themselves never move. A 1 MiB binary sent to 100 receivers exists once in memory, with 101 references to it (sender + 100 receivers).

A ProcBin is a library card. Sending it doesn't photocopy the book — it just hands out another card to the same book on the same shelf.

9. The shared zone — refcounted off-heap binaries

Large binaries don't live on any process heap. They live in the shared zone: individually-allocated structs scattered through the system allocator, each carrying an atomic refcount, its bytes, and its own destructor function pointer. When the refcount hits zero, the destructor runs and the memory goes back to the system allocator.

No central registry. No mutex. Each SharedBin is its own allocation:

  struct SharedBin {           // 40 bytes of fields, 48 with alignment padding
    refcount:   AtomicUsize,                    // 0..8
    bit_len:    u64,                            // 8..16  (length in bits)
    bytes_ptr:  *const u8,                      // 16..24 → separate Box<[u8]>
    bytes_len:  usize,                          // 24..32
    destructor: fn(*mut SharedBin),             // 32..40
  }

The struct is 16-byte aligned, the same as everything on the process heap, and that is load-bearing rather than cosmetic. A ProcBin keeps this address in its first word, and the first word is also where the collector writes a forwarding marker — a pointer with a set low nibble. At 8-byte alignment about half of all SharedBin addresses have a set low nibble, so a perfectly live ProcBin would read as already forwarded: the sweep would take the SharedBin itself for a relocated stub and write into it. Aligning to 16 means no real address can ever be mistaken for a marker.

The bytes live in a separate Box<[u8]> rather than inline, so the destructor can free the bytes and the SharedBin struct independently. The destructor field is set at allocation time:

  • shared_bin_destructor_heap — for runtime-allocated bins; reconstructs both boxes and drops them.
  • shared_bin_destructor_noop — for compiler-baked static bins whose bytes live in .rodata; the destructor is reachable in principle but pinned by a static refcount of 1 so it never actually fires.

How a process points at one — ProcBin

A process can't hold a raw *mut SharedBin directly; the GC wouldn't know what to do with it. Instead, each reference goes through a small heap object:

  ProcBin (16 bytes, lives on the process heap):

  ┌───────────────────┬───────────────────┐
  │  shared_ptr (8)   │  mso_next (8)     │
  │  → SharedBin      │  → next ProcBin   │
  └───────────────────┴───────────────────┘

ProcBin refs use the heap-object TAG_PROCBIN kind. The shared_ptr field points outside any heap arena, so the collector treats the ProcBin as a raw payload object with no fz value children.

The mso_next link at +8 makes ProcBins their own intrusive linked list. When a ProcBin survives, Cheney writes only a forwarding marker (to-space address with a set low nibble) at +0; +8 is left intact so the MSO sweep can continue through the from-space chain. The surviving shared_ptr is read from the to-space copy, while a dead ProcBin's shared_ptr is still read from +0 in from-space.

Allocation policy

When code constructs a bitstring, Heap::alloc_bitstring picks the storage based on size:

  if bytes.len() > SHARED_BIN_THRESHOLD_BYTES {   // = 64
      shared_ptr = shared_bin_alloc(bytes, bit_len);
      return self.alloc_procbin(shared_ptr, 0);   // whole binary
  }
  // small: inline TAG_BITSTRING object on the process heap

Render, bit-matching, and equality all go through small dispatch helpers (bitstring_bit_len, bitstring_byte_ptr, is_bitstring_like) that read from the right place based on the ref's high-bit kind tag. Callers don't know or care which storage they're looking at — the behaviour is identical.

Matching a tail copies nothing

A ProcBin doesn't name "the shared binary" — it names a byte-aligned suffix of one. Alongside shared_ptr it carries a byte_offset, and its length is whatever remains after that offset. The whole binary is simply the suffix at offset 0.

That is what makes a byte scanner cheap. This clause asks for a suffix:

  defp walk(<<_c, rest :: binary>>, n), do: walk(rest, n + 1)

so rest becomes another stub over the same bytes at offset +1, and nothing is copied. Suffixes at or below the 64-byte threshold are still copied into an inline bitstring: at that size a copy is smaller than a stub, and it keeps a short tail from pinning a long buffer alive.

Without this, each step copied the whole remainder, so scanning n bytes copied n + (n−1) + … bytes. Decoding a 919-byte JSON document copied 1.4 MB; it now copies the document once.

Why a suffix and not any window.
Every shared buffer is allocated with one extra zero byte, so a binary can be handed to C as a NUL-terminated string without copying. A suffix ends exactly where that NUL is, so it inherits the guarantee; an arbitrary window in the middle would not. So a window in the middle cannot be built: alloc_procbin takes an offset and derives the length, rather than accepting one.

Lifetime — retain, release, sweep

Three operations move the refcount:

  • Allocate a new SharedBin (refcount = 1). The newly allocated ProcBin is the sole reference.
  • Send across processes: deep_copy_any_value_ref retains the shared_ptr (refcount ++) and allocates a fresh ProcBin in the sender's gift window; the receiver adopts it when it grafts the segment. Bytes don't move.
  • Die: either a ProcBin fails to survive a GC (refcount −− in the MSO sweep), or the entire heap is dropped (every ProcBin still on mso_head is released by Heap::drop before the blocks return to the pool).

Release uses the canonical Arc pattern: Release on the decrement, an Acquire fence on the final 1→0 transition, then the destructor runs. Last one out turns off the lights.

Why this needs no locks.
The system allocator handles concurrent Box::new from any worker. The refcount is atomic. The MSO chain is per-heap and per-heap is per-process, so only one worker accesses it at a time (scheduler invariant). fz values are immutable, so there are no write barriers. There is no central registry to contend on.

Object size on the process heap

Because binaries above 64 bytes go off-heap, the process heap deals only with small inline objects, cons cells, tuples, maps, closures, resources, and ProcBin stubs — in practice well under the table's last entry (~7 MiB). The grow logic in Heap::alloc() picks the smallest capacity that fits any individual object; an object larger than the whole table gets a block of exactly its size.

10. Return-demand destination planning

Return-demand destination planning is how the compiler chooses the result context for a call. A call is not only "call this function"; it is "call this function, and put the result into this typed hole." The planner records that choice, and native codegen lowers the selected calling convention. When the chosen context has to travel at runtime, that lowering becomes destination passing.

The capability has two parts: how the result is delivered, and what context is already available. A function can return a material value or return tuple fields directly, and a tail-call edge can forward the caller's own demand. The executable context plan is a typed compiler fact attached to a specific caller specialization and callsite. These are still ordinary immutable data constructions: no published tuple, list, or map is mutated after publication.

The important boundary is observability. Return-context motion may not cross an extern call, a receive, scheduler-visible process operation, halt, unknown closure call, or Process.heap_alloc_stats(). Allocation alone is not source-visible, but allocation timing becomes visible when a program reads the current process allocation counters.

Each list construction may retain an exact, traced source cell. Unchanged contents return that source even when shared. Changing the cell requires both construction-owned rewrite permission and a clear alias bit. Calls and structural tuple fields classify actual ownership as Transfer or Share; overlapping inputs and caller-retained values are shared before entering the callee. One-shot continuation roots do not independently expose the old language value.

A marked cell certifies a closed shared spine: its tail is marked too. Sharing stops at the first marked cell. Materialized list heads, tuple/struct fields, closure captures, and map keys/values publish their contained lists during their existing construction loops; there is no extra structural runtime scan.

Extern calls do not publish their arguments for alias tracking. If an extern wants to retain a value after returning, the extern must copy it.

Cross-process send is a copy boundary, not an alias boundary. The sender deep-copies the message graph into a gift before queueing it on the receiver, so the sender's list cells need not be marked aliased just because they were sent. A singly copied list can remain unshared; repeated references and copied container fields protect sharing in the receiver. Self-send copies nothing: the sender's own reference enters the mailbox, and the compiler's call-site Share publication is what marks a list the sender still names. Inside a single heap the alias bit is one-way, so a rewrite miss falls back to allocation rather than rewiring a value another observer may still hold.

11. Heap allocation stats

Each process heap records allocation requests by kind. The counters are runtime process facts, separate from compiler2 telemetry, which reports compiler decisions. They are reset after process setup, so bootstrap wiring does not pollute fixture baselines. Static closures and halt continuations are read-only data in the compiled program, not heap allocations, so they never appear in the counters.

Process.heap_alloc_stats() exposes the current process snapshot as a map. The runtime reads the counters first and then allocates the map, so the returned value does not count itself. A later stats call can include the map allocated by an earlier stats call.

The total keys are :allocs and :bytes. Per-kind keys use the pattern :K_allocs and :K_bytes, where K is one of list_cons, struct, closure, map, bitstring, procbin, shared_bin, scalar_box, frame, resource, or other. Heap object bytes are 16-byte aligned request sizes. Frame bytes are the aligned frame allocation size even though frames are allocated outside the bump heap.

:shared_bin_allocs and :shared_bin_bytes count the off-heap byte buffers behind large binaries, and are deliberately NOT part of :allocs / :bytes — those bytes never live on the process heap. They are the counters that tell copying from sharing: a ProcBin stub costs the same either way, so without them a binary copied byte for byte looks identical to one that shares an existing buffer.

The stats answer "how much memory did this process request from the runtime allocation paths?" They do not answer "how many bytes survived GC" or "what did the compiler decide to lower." Use GC stats for live-set facts and compiler stats for lowering facts.

12. What comes next — generational GC

The most expensive property of flat Cheney GC: it re-copies the entire live set on every cycle. A loop that builds a list of 1000 elements copies 100 + 200 + … + 1000 = O(N²) bytes total if GC fires every 100 allocations.

Generational GC fixes this by splitting the heap into young and old generations. A minor GC only collects new objects; old objects stay put. The list tail — allocated many GC cycles ago — is never re-copied in a minor collection. Total work: O(N).

Why fz gets generational GC almost for free

Generational GC normally requires write barriers: if an old object is mutated to point at a new object, the GC must record it (otherwise the new object looks unreachable from the old generation). Every pointer write needs an extra store — significant overhead.

fz is purely immutable. Once an object is allocated and initialised, it is never modified. Old objects can never gain new-object references after promotion. No write barriers needed.

The watermark already exists. After any GC, objects below the watermark are "old"; objects above are "new." A minor-collection pass would:

  • Trace from runnable_closure and mailbox as roots.
  • Copy only objects above the watermark (young generation).
  • Leave objects below the watermark untouched.
  • Reset the watermark to bump_top after collection.

The MSO sweep changes in form but not in kind: minor collections release refs only for ProcBins that died in the young generation; major collections sweep both generations. The same forwarding-marker check that powers the current single-generation sweep generalises directly.

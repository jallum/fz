1. Values — any value refs and container storage

fz has one dynamic value abstraction: AnyValueRef. It is one opaque word. Its tag says what kind of value it names. For an object, an integer or a float its address points at the payload; an atom ref holds the atom id in the address field and points at nothing. Known typed lanes still carry raw i64 or f64 when the type is known; boxing an integer or float into an any value ref is the last resort for any boundaries such as send, dynamic container reads, and generic runtime calls. An atom needs no box: its ref is the atom id under the atom tag.

The storage shape is chosen by where the value lives:

  • AnyValueRef: one opaque word used at dynamic boundaries. Its high tag bits say whether the address points at an int, float, atom id, list, map, tuple/struct, closure, binary, or resource. It may survive allocation, yield, or GC only when stored in a traced root owner such as a parked receive record.
  • Container-local typed storage: used inside lists, maps, tuples, and closures. Containers store compact payload words and the minimal kind metadata their layout needs. This is private object layout, not a second value abstraction.

Heap objects are 16-byte aligned, so the low 4 bits of any real heap address are clear. The only use of those bits is the GC's forwarding marker. AnyValueRef words, and every heap-object word that names another object, carry the logical kind in architecture-owned high bits and must only be inspected through the AnyValueRef API.

AnyValueRef uses the runtime ValueKind tag values: 0 Null, 1 List, 2 Map, 3 Struct, 4 Closure, 5 Bitstring, 6 BinView (a binary view), 7 Resource, 8 BinRef, 13 Int, 14 Float, and 15 Atom. The empty list is a null-address List ref. The tag lives at bit 56 on arm64/TBI and bit 57 on x86_64; callers use the API rather than those bit positions directly.

The canonical object-local kind table is below. Heap objects use these values for compact metadata. Generated code and runtime helpers project to or from AnyValueRef through typed APIs; persistent dynamic values are not carried as public word-plus-kind pairs.

A value ref is a stamped envelope. At dynamic boundaries the stamp is on the envelope itself. Inside containers, the envelope can be packed more tightly because the container layout already says where the stamp lives.

A few consequences of this layout:

  • The low nibble of a live pointer is zero. Heap objects are 16-byte aligned. Heap tags 0x1 through 0x7 identify the object kind in the high bits; masking them off recovers the address, and the low nibble is never part of either.
  • Integers and floats are raw in typed storage. A local tag 0xD means the payload is a full signed i64. A local tag 0xE means the payload is raw f64::to_bits().
  • Specials are atoms. nil, true, and false are reserved atom IDs. Empty list has a dedicated AnyValueRef tag at dynamic boundaries; inside list links it is represented by the empty-list sentinel used by that layout.

The GC follows heap-kind tags 0x1 through 0x7. Immediate side-band tags pass through unchanged. When Cheney relocates an object, it overwrites one marker word of the from-space copy with to_space_address | 1; later scans read that word and treat any set low nibble as "already forwarded". The marker word is word 1 (the link) of a list cons and word 0 of every other kind, and each kind lays that word out so a live value has a clear low nibble: a struct, closure, bitstring or map header keeps four clear bits below its fields, and a binary view, BinRef or Resource keeps a 16-aligned pointer there. One read decides; no second word is consulted.

Objects the program carries in read-only data (static structs, static closures and halt continuations) are never on a heap. Every reference to one has a single literal bit set in its address word, above the kind field and at the same position in a ref word, a field or capture payload, a map entry, a list head and a list link. The collector and deep copy read that bit: a tagged reference is left in place or shared, an untagged one is a heap pointer and is copied. Nothing walks the heap's block list to decide. Debug builds cross-check the bit against the block ranges and assert that an untagged pointer lies in from-space and a tagged one does not.

Old per-float heap objects are retired. Floats in typed code travel as native f64; floats stored in containers are raw bits. A boxed integer or float is allocated only when an any boundary needs a AnyValueRef; an atom ref is formed from its id and allocates nothing.

Container-local layouts

Generic containers store raw 64-bit payload words and keep compact kind metadata beside those payloads. The canonical tag values above are shared by heap pointer tags and container-local metadata.

List cons cell:

  offset 0:  head: u64
  offset 8:  link: u64
             high metadata = alias flag + head kind tag
             address bits  = next cons address, or 0 for end-of-list
             low 4 bits    = clear pointer-alignment bits

The cell itself is named by a TAG_LIST pointer. Empty list is the null next address. Improper-list representation is outside this first layout migration and must be handled by a follow-up if encountered. The alias flag is a conservative reuse guard: runtime helpers may mark a cons aliased. Compiler-facing reuse helpers treat an aliased source cell as an allocation miss: unaliased cells may be relinked in place, while aliased cells use fallback allocation to produce a fresh cons with the same head and the requested tail.

Map:

  offset 0:                      header: count << 4
  offset 8:                      tag_bytes: [u8; N], padded to 8-byte alignment
  offset 8 + pad(N, 8):          keys:   [u64; N]
  offset 8 + pad(N, 8) + 8N:     values: [u64; N]

Each map entry has one tag byte: high nibble = key kind, low nibble = value kind. Total size is 8 + ceil(N/8) * 8 + 16N, then rounded to the next 16-byte boundary. A map still under construction (an unpublished destination) has a different header: bit 63 set, the number of entries filled so far at bit 33 and the capacity at bit 4, each 29 bits wide. Freezing it writes the published header.

A map with more than 32 entries is a hash trie. Each node is a Map object whose header has bit 62 set; it keeps the layout above for its own entries and appends one word per child after the values:

  header:  bit 62 | total << 36 | child_map << 20 | data_map << 4
  then:    tag_bytes, keys, values (one per bit of data_map), children (one per bit of child_map)
  collision node: bits 62 and 61 set, entry count at bit 36, entries and no children

A key's 64-bit hash (term_hash) picks a slot per level, four bits at a time, top bits first. A slot holds an entry or a child, and a node exists only where two or more keys share the path, so a key set has exactly one trie. Keys whose whole hash is equal share a collision node. The root's total is the map's size. The low nibble of every header is clear, so the forwarding marker works on a node as on any other object. A map of up to 32 entries is a flat array, and enumeration order is key order for it and node order (a function of the hashes) for a trie.

A put or a delete on a trie copies the nodes on the path from the root to the key's slot, which is a handful of nodes whatever the map's size, and shares every other node with the map it was given. A node left with one entry is pulled up into its parent, which keeps the one trie per key set. A put that takes a flat map to 33 entries makes a trie, and a delete that takes a trie to 32 makes the flat array again. An update, %{m | k: v}, of a trie is a put of that key on the trie itself.

Dynamic roots:

  AnyValueRef    // one word; tag + address

Mailboxes, parked selective receive pins, matcher inputs, matcher outputs, and scheduler handoff values use AnyValueRef. Heap-object refs point at heap objects and are traced by object layout. Integer and float refs point at boxed scalar payloads and have no children. Atom refs carry their id and have no children. Sentinels have no children.

There is deliberately no generic persistent word-plus-kind carrier. Anything that survives scheduler or GC boundaries is either a AnyValueRef root or an ordinary heap object reached from one. Container-local metadata is private to the object layout.

Destination planning:

Destination planning lets the compiler decide where a value should be built or delivered before it starts building it. Destination passing is the lower-level mechanism used when that plan has to carry an unpublished construction location or hidden call context through IR or native ABI. The destination is private process-local construction state. Once it is frozen or returned to user code, the result is an ordinary immutable value.

For tuple-shaped results, the compiler can avoid a temporary tuple when the caller immediately projects the fields:

  {lo, hi} = partition(p, rest, [], [])

The selected native path can deliver lo and hi directly to the continuation as independent values. No published tuple is mutated, and no tuple object has to exist just to be projected.

For recursive list code, the compiler can pass the final tail as context and allocate immutable cons cells in front of it:

  append(qsort(lo), [p | qsort(hi)])

That shape can be executed as:

  hi_tail    = qsort_into(hi, outer_tail)
  pivot_tail = [p | hi_tail]
  qsort_into(lo, pivot_tail)

The cons cells are still ordinary immutable list cells on the process heap. The compiler only chooses their tail before building the prefix.

Source-level structural helpers do not need to become BIFs just to be predictable. A plain recursive append:

  def append([], ys), do: ys
  def append([h | t], ys), do: [h | append(t, ys)]

still compiles as source code. In the append fixture, append([1, 2, 3], [4, 5]) allocates the five list-literal cons cells and no prefix-copy cons cells, with no tuple/struct or map allocation in the value path. Each recursive append construction retains its exact source cell; there is no append BIF.

Map construction:

Maps are immutable values. A map literal or update is lowered through an unpublished process-local destination, linear put operations, and a freeze that publishes the immutable map:

  dest = fz_map_dest_begin(extra=2)        // unpublished storage
  _    = fz_map_dest_put(dest, k0, v0)
  _    = fz_map_dest_put(dest, k1, v1)
  out  = fz_map_dest_freeze(dest)          // immutable canonical map

The destination lives on the owning process heap and is not visible as a published value. Freeze sorts by runtime map ordering, removes overwritten duplicate keys, and returns the canonical immutable map. Each put hands over its key and its value as the word the map stores and the value's kind, so an integer or a float goes in without a box; a key or a value whose kind is known only when the program runs has its kind read from its reference. Map.put takes the same two words through fz_map_put. Dynamic map reads still return AnyValueRefs when the caller needs an any.

An update, %{m | k: v}, starts from a copy of m instead of empty storage, and its puts may only replace keys m already has:

  dest = fz_map_dest_begin_update(m)       // m's entries, unpublished
  _    = fz_map_dest_put(dest, k, v)       // replaces, or notes a missing key
  out  = fz_map_dest_freeze(dest)          // the map, or the miss sentinel

When a key was missing, freeze answers the miss sentinel instead of a map, and the program raises KeyError as Elixir does. A struct updated this way stays the same struct.

When the compiler knows which struct the base is and every key names one of its fields, the update skips the destination and writes the replaced fields directly. If nothing else can hold the base, it writes them into the base itself. A loop that threads one struct through its updates then rewrites that one struct at each step instead of copying it:

  def count(c, 0), do: c
  def count(c, k), do: count(%{c | n: c.n + 1}, k - 1)   // one store per step

Two answers have to agree. The compiler grants the rewrite only when the code after the update never uses the base again. At run time the struct's header carries a shared mark, set the moment a second holder could appear: when the struct is passed to a call whose caller still reads it, stored into a tuple, struct, list or map, captured by a closure, sent as a message, or kept by a collection. A marked struct is copied, so anyone still holding it reads its old fields.

Return-demand destinations:

Some destinations are selected at call boundaries instead of local literal sites. The planner records these as ReturnDemand capabilities on the selected SpecKey. TupleFields delivers a tuple result as independent continuation values; a tail-call edge can instead forward the caller's own demand. Recursive list code needs no list-tail delivery shape: it builds the list forward with an O(1) continuation (tail recursion modulo cons) plus list-retention transport. Codegen implements the planner-selected capability; it does not guess from source names.

For recursive list code this is tail recursion modulo cons: the compiler passes the tail context explicitly, then allocates immutable cons cells in front of that tail. In fixtures/quicksort, the native paths pin list_cons_allocs = 11, list_cons_bytes = 176, struct_allocs = 0, and headline heap bytes 176.

Other heap layouts:

  • Struct: offset 0 header schema_id << 32; offset 8 one 8-byte slot per field, then one kind byte per field, padded to a whole word; total size is align16(8 + schema payload). Compiled code allocates the object with one runtime call and stores each field whose kind it knows in place.
  • Closure: offset 0 header (denotation << 32) | (arity << 20) | (flags << 4), where flags hold the captured count and halt kind and arity is below 4096; offset 8 fn_ptr: u64; offset 16 raw capture words; capture kind bytes follow the raw words and are padded to 8-byte alignment.
  • Bitstring: offset 0 header bit_len << 4; offset 8 the bytes and one trailing zero byte, padded to 16-byte alignment.
  • BinView (a binary view): offset 0 header bit_len << 4 with the shared mark, as a bitstring's; offset 8 bytes_ptr; offset 16 tagged pointer to its heap's BinRef (traced by the collector); 24 bytes of fields in a 32-byte slot.
  • BinRef: offset 0 shared_ptr; offset 8 off_heap_next with the creating site in its low nibble; 16 bytes total.
  • Resource: offset 0 resource_ptr; offset 8 off_heap_next; 16 bytes total. The destructor lives on the shared off-heap Resource.

2. The process heap — bump allocation

Every fz process has its own private heap. No sharing, no locks. Allocating is a pointer bump — two comparisons and an increment on the fast path.

  Process heap (one block, contiguous):

  block_start                                             block_end
      │                                                       │
      ▼                                                       ▼
      ┌───────────────────────────────────────────────────────┐
      │ allocated objects ← bump_top                          │
      └───────────────────────────────────────────────────────┘
                            ▲
                         bump_top
Think of the heap as a stack of paper. To "allocate," you write your object on top and move a finger (the bump pointer) down by however many lines you used. Nothing else needs to happen on the fast path.

Heap objects are 16-byte aligned and share no universal header. The kind rides in the high bits of the reference that names the object, and each kind has its own prefix and size function.

Ordinary large objects — tuples with many fields and maps with many entries — live on the process heap and grow into bigger blocks as needed. Bitstrings above SHARED_BIN_THRESHOLD_BYTES (64 bytes) don't live on the process heap. Instead the heap carries a 32-byte BinView view that names a 16-byte BinRef, which points into the shared zone.

Block pool and block capacities

Blocks come from a per-thread pool sized by a Fibonacci-then-geometric size table (1 KiB up to ~7 MiB); a heap's tip starts at the first entry and climbs the table and stays at the last entry. When a block fills before GC fires, a new block one step up becomes the tip and the old one joins blocks, recorded with its fill and capacity. An object larger than that step is not made the tip: it gets a block sized for it, parked on blocks straight away, and the tip keeps filling. All parked blocks are reclaimed at the next GC.

The table has neither a floor nor a ceiling on what a block may be. A request below the first entry gets a block of exactly its size (rounded up to 16 bytes), and the pool keeps a free list for each such multiple of 16, so small blocks are recycled like any other. A request above the last entry also gets a block of exactly its size; that block comes from the system allocator, not the pool, and goes back to it when it is released. An object larger than the last entry is copied like any other when the collection that reaches it releases the block.

The gift window

A heap can lend its allocation path to a copy whose result belongs to another heap. Cross-process send is its user: the sender copies a message, or a match's roots, inside one, and the segment waits on the receiver's in_queue until the receiver's next dispatch moves it into the mailbox, where it waits again until a receive takes the message and grafts it.

The sender measures first. measure_deep_copy walks the value set the way the copy will and returns the bytes it will allocate. A send copies without preserving sharing, as BEAM's does: a subterm the message reaches twice is copied twice and counted twice. Heap::begin_gift takes that figure, sets the current tip aside and installs one block of the smallest capacity that holds it (a pooled block of exactly that size when it is below the table, so a 16-byte message occupies a 16-byte block, and an exact block from the system allocator above it). The copy runs through the ordinary bump path and fills the block without overflowing it. Heap::end_gift asserts the block's fill is exactly the measured bytes, turns the block into a GiftSegment and puts the saved tip back with its free space intact. The segment carries that one block (with its fill), the prefix of the off-heap chain that the window produced (BinRefs and Resources together), and the number of objects allocated. The heap's allocation statistics stay with it, its live_count goes back to what it was. A collection cannot run while a window is open.

The receiving heap calls Heap::graft: the segment's block is parked among the young blocks, and its off-heap prefix is spliced ahead of the receiver's young chain. Every parked block counts toward bytes_used by fill, never by capacity, so a kilobyte block holding one cons cell is sixteen bytes of bytes_used. The same fill counts toward the next collection exactly as allocation does, and it is reported as received_bytes in the next fz.runtime.gc event. graft leaves live_baseline and the old blocks alone. A segment that is dropped without being grafted releases its block and every stub's off-heap reference.

A message waits outside the heap until a receive takes it. The process's Mailbox holds its messages in arrival order, each with its segment, ungrafted and not a root, and Mailbox::take grafts the segment as the receive removes the message. A message the process sent to itself is copied into a segment like any other.

The off-heap chains

Each heap carries one intrusive linked list of every BinRef and Resource it owns, as OTP keeps one off-heap list for BinRefs and magic binaries alike; the kind tag of each link says which of the two it names. The head pointers live on the heap (off_heap_head for the young list, off_heap_old_head for the old); the "next" link lives at offset +8 inside each stub, BinRef and Resource alike. A binary view is on no chain: many views of one buffer share the one BinRef. "MSO" is the historical BEAM name — "Mixed Set / Off-heap" — for the list of objects whose real bytes live elsewhere.

The off-heap chains are a "things to clean up later" list. Every time the heap makes a BinRef or Resource, it adds the stub to the chain. After each GC, we walk the chain to figure out which stubs survived and which need to release their off-heap payload. The chain is split by age: off_heap_head holds stubs made or received since the last collection; off_heap_old_head holds the ones a collection already kept. See §9 for the details.

3. Reductions, collection timing, and boundary GC

Processes run on a reduction budget. Every compiled or interpreted loop back-edge spends budget. When the budget reaches zero, the process materializes a scheduler-owned continuation closure and yields. Collection timing is separate: allocation makes the heap due for GC, but it does not spend reductions and does not force a yield.

should_gc

Every Heap::alloc() call is a bump and nothing else. Whether a collection is due is a question about the heap's state, answered by Heap::should_gc when the scheduler asks at a boundary: the fill of the young blocks (the tip and every parked block) against the heap's live_baseline, held between the 4096-byte budget floor and the largest pooled block. The baseline is the fill of the old blocks: a collection sets it to the bytes that survived, and allocation and graft leave it alone. The young blocks include the blocks of the messages receives have taken. A heap holding N old bytes is therefore due a collection once it has allocated or received N more, and never more than the largest pooled block (about 7.4 MB): a large heap keeps its young data in one pooled block, so a collection neither obtains nor returns a large block. A collection that reclaims those bytes answers the question by itself; nothing is cleared. If an allocation no longer fits in the current block, the heap parks it in young_blocks for the next Cheney pass and installs a tip one step up, unless the object is larger than that step: then the object gets a parked block of its own and the tip stays.

  bump_top += size
  if bump_top would cross block_end {
      if size > next_block_capacity(block_size) {
          young_blocks.push(block sized for the object)   // tip unchanged
      } else {
          young_blocks.push(tip); tip = block one step up
      }
  }

  should_gc = young_bytes >= max(live_baseline, BUDGET_FLOOR)
              || young_binary_bytes >= max(held_binary_bytes, 256 KiB)

  // as the heap answers it, in one compare:
  should_gc = bump_top >= collect_at

collect_at is the bump pointer at which the young bytes reach the budget: the tip's start plus the budget less the bytes of the parked blocks. The heap recomputes it where an input changes (a block is parked or grafted, a tip is installed, a collection ends) and never in the compiled bump path, which moves only bump_top. When the binary budget is reached it is set to null, so the same compare collects. Debug builds check the compare against the formula above at every question.

Compiled yield telemetry still samples the margin before and after the reduction-yield slow path, so max_yield_continuation_bytes includes the continuation closure, scalar boxes, and materialized continuation state observed while yielding.

The back-edge check

Every loop in fz is a tail-recursive call. The compiler uses Tarjan SCC (already run by the type system) to figure out which tail calls are back-edges: a call whose callee is in the same strongly-connected component as the caller. Self-recursion is the easy case; mutual recursion (f → g → f) is covered automatically.

At every back-edge call site, codegen emits:

  gv        = global_value.i64 %FZ_REDUCTIONS_REMAINING
  remaining = load.i32 gv+0
  remaining = remaining - 1
  store remaining, gv+0
  brgt remaining, 0, $fast

  ; slow path (budget exhausted):
  call fz_yield_slow_path_begin()
  cont = place closure(next_loop_fn, argc, halt_kind, code_ptr)  ; inline bump, header and code address written in place
  store arg0, cont.capture[0]
  store arg1, cont.capture[1]
  ...
  call fz_yield_mid_flight_report(cont, remaining, YIELD_REASON_REDUCTIONS)
  return [YIELD_PTR]                          ; sentinel; scheduler sees it and re-queues

  $fast:
  return_call loop_fn(args...)                ; unchanged hot path

The slow path only fires when the process has spent its quantum. Nothing else makes a process yield: a heap that is due for collection waits for the process to reach a boundary.

4. Collection — Cheney with explicit roots, minor and major

When the scheduler finds a heap due at a boundary, all live data is reachable from the roots the process holds: the park record's outcome closure templates, after body and pinned values, and the runnable continuation closure. No stack scan, no register enumeration.

Blocks have an age. The tip, the parked tips and huge blocks are young, and so are the blocks of the messages receives have taken. The blocks a collection filled with survivors are old. A minor collection takes only the young blocks as from-space; old blocks stay where they are and are not traced through, because nothing old points at anything young. A major collection takes every block. A heap goes major when its old bytes exceed twice what the last major left (and never while it has nothing old); otherwise it is minor. The fz.runtime.gc event reports which it was in generation.

  from-space (a minor takes the young blocks; a major takes all)
  ┌────────────────────────────────┐
  │ [dead]  [dead]  [live]  [dead]  │
  │      scheduler roots point ──►│──►closures + AnyValueRefs
  └────────────────────────────────┘
           │ Cheney BFS copy │
           ▼
  to-space (a fresh tip; copies park blocks as it fills)
  ┌─────────────────┐
  │ [live][live][live]│
  │         bump_top│
  └─────────────────┘
  from-space → pool (freed)
Cheney is the world's tidiest move-out. You bring a fresh empty room (a fresh tip). Starting from one pointer, you copy every live object across. Once you're done, you walk out and burn the old room. Nothing dead gets a ride.

A message a receive has taken is young. If it is dead at the next collection a minor collection reclaims its block, and if it is live the collection copies it once and it is old from then on. The received bytes count toward the next collection like allocation, so a heap that takes in a lot of mail collects often enough that the dead mail does not pile up. The accepted consequence: a message that waits in the mailbox is held in its segment, outside the heap and outside the young-byte count, until a receive takes it or the process exits; a process whose receives skip a message holds it that long.

To-space is a chain

The collector installs a fresh tip and every copied object goes through Heap::bump_to_space: when the tip is full it is parked on young_blocks and an overflow block is installed, the smallest class first (the table's last entry when the guess is at least that large) and one class up for each later overflow, never past the last entry; an object larger than that step is parked alone in a block of its own with the tip untouched. The scan pops a worklist of copied objects rather than walking an address, so to-space needs no contiguity: it is the new tip plus the parked blocks.

The to-space block's capacity is only a guess at how many bytes the pass copies: a major starts from live_baseline; a minor starts from the bytes the previous minor pass copied, since a major's copy says nothing about what the young generation keeps. Both are no smaller than the smallest tip and no larger than the table's last entry (~7 MiB): a young tip or to-space past that is a chain of last-entry blocks, which the pool recycles. A guess that is too small costs overflow blocks sized for the overflow, not for the whole guess, so the room the pass leaves unused in old blocks is bounded by the overflow (to_space_capacity_bytes less copied_bytes in the gc event; the telemetry writer sums the capacity over the old blocks the pass filled). The blocks the pass filled become old; an empty to-space tip is released. The heap then installs a fresh young tip sized for live_baseline before the from-space blocks go back to the pool, or to the system allocator when exact. The from-space blocks belong to the collection's Collected until it is dropped, so the telemetry writer reads them as they were: from_space_capacity_bytes and blocks_released in the gc event are computed there from those blocks, not stored by the collector. The worklist and the two block lists a collection uses (the young blocks and the from-space, which swap roles at each collection) are kept by the heap and never freed between collections.

After a major scan, live_baseline is the sum of the sizes of the objects copied; after a minor it is the old bytes kept plus the bytes copied. That feeds the next GC's trigger. copied_bytes is what this pass moved and live_bytes is the new baseline, so after a minor it still counts old data that has died until the next major. young_bytes is what the process allocated since the previous pass and young_budget the amount at which the pass became due. The trigger is only asked at the end of a quantum, so a busy process can allocate far past its budget first.

A shared binary's bytes live off-heap and the heap holds only a small BinRef, so the heap's own byte count cannot see them. A second budget counts them: young_binary_bytes is the capacity of the shared buffers the process made since the previous pass (a filled buffer, or the new buffer of a concatenation; an in-place append adds nothing), and binary_budget is the binary bytes the heap still held after that pass, never less than 256 KiB. The survivors are measured in the off-heap sweep: a major pass counts every BinRef it kept, a minor pass adds the young ones it kept to what was held. Either budget makes a pass due. When an allocation brings the young binary bytes to the budget the process's quantum ends at once, so the pass runs at that boundary instead of after a full quantum of further binaries.

Each copied from-space object gets an in-band forwarding marker written into its marker word: to_space_address | 1. Any other pointer to the same object reads that marker, strips the low nibble, and is rewritten to the same-kind to-space pointer. This is how shared structure stays shared after collection without side tables.

5. Mid-flight GC — collecting a running loop

When the back-edge slow path fires, the process is mid-loop. The compiler turns the in-flight state into the same shape the scheduler already knows how to run: a zero-arg closure. The closure's captures are the loop args being passed to the next iteration, plus the current continuation.

  struct Process {
    ...
    runnable_closure:      *mut u8,       // tagged closure to run next; null = none
    reduction_yields:      u64,           // ordinary budget exhaustion
  }

Closure captures use the regular container-local layout: raw payload words plus compact kind bytes stored inside the closure object. There is no fixed argument limit, no side table, and no separate GC storage. The GC roots the closure, follows its captures, and forwards anything reachable. Resuming is just running the closure.

A back-edge yield is like a relay runner setting their baton down in a labelled box before stepping aside. The collector tidies the track; the next runner picks up the baton from the box and keeps running.

Continuation closure

For each back-edge callee shape, codegen emits a small closure entry alongside the function body:

  fz_mid_flight_cont_fn42(self):       ; SystemV, scheduler-callable
    return fz_mid_flight_cont_fn42_tail(self)

  fz_mid_flight_cont_fn42_tail(self):  ; Tail-CC
    r0 = load_capture(self, 0)
    r1 = load_capture(self, 1)
    ...
    return_call fn42_body(r0, r1, ...)

The SystemV entry lets the Rust scheduler call the closure through the normal fz_resume path. The Tail-CC sibling reloads captures into the callee's native ABI and tail-calls the loop body.

A long body shares one frame

A function that calls sixteen or more times and holds values across the calls runs its calls' continuations in one heap frame instead of one frame each. The first continuation is built with a slot for every value the body holds; each later one is handed the same frame, so a value is written once and read where it is used, and the program's code and frames grow with the number of calls. A step that resumes does not give such a frame back, because the steps after it still read it. When a value is last used its slot is cleared, so the frame does not keep a dead list alive.

A collection keeps the frame in an old block, and a write into an old object that names a young one would hide the young object from the next minor collection. So before every write the step checks that the frame is in the newest block; if it is not and the frame is old, the frame is copied to the tip and the write goes to the copy. Each process counts these copies in its frame_copies telemetry.

6. GC roots and the off-heap sweep

The GC traces only explicit roots. Everything else is dead.

One method, Process::collect, builds the root set from the process and calls the one collection entry, Heap::collect. Every scheduler reaches the same root set, and each slot holds its forwarded value when the call returns.

The roots of a process
runnable — a zero-arg closure capturing the next loop state. It is traced through the normal closure layout.

The park record — the receive's clause-body closures, its after body, and its pinned values (heap values the matcher compares against). The matcher reads the pinned values whenever a message arrives, so they move with everything else. Every parked receive carries a compiled matcher; the catch-all form receive do msg -> msg end is the accept-any shape.

process.mailbox — not a root. Every message waits in its gift segment outside the heap, a self-sent one included, so a collection neither traces nor moves it.

Transient values — whatever the caller holds across the call.

Gifts waiting in the delivery in-queue and messages waiting in the mailbox are not roots. Their blocks join the heap only when they are grafted (a match by drain_in_queue, a message by the receive that takes it), and every reference in a gift points into its own segment. Process::collect holds the delivery lock for the whole pass, so a sender cannot probe the park record while it moves.

The interpreter keeps a parked receive's environment and continuations in its own structures. It passes their heap refs to Process::collect as transient roots and writes the forwarded refs back.

off-heap sweep — keeping shared-zone refcounts honest

After Cheney's BFS scan completes and before from-space is freed, the GC walks the off-heap chain of the from-space once: a minor walks only the young chain, a major walks the old chain too. Each entry is a BinRef or Resource stub that was in from-space. The forwarding marker Cheney writes into word 0 of every copied stub is the entire liveness signal. A live view reaches its BinRef through word 0, so a BinRef is copied once however many views name it, and a BinRef no live view names is unreached — no separate bookkeeping. One function, off_heap::sweep, decides every stub, after a collection and when a process exits (an exit is not collected; it is the same walk with nothing live and no to-space):

  cur = young head                          // a major also walks the old head
  new_head = null
  while cur != null:
      kind = kind_tag(cur)                  // BinRef or Resource
      marker = read u64 at addr_of(cur)+0
      next = read_off_heap_next(cur)             // from-space link survives
      if low4(marker) != 0:
          new_addr = strip_low4(marker)     // to-space copy
          link new_addr into new_head       // survived; rejoin the chain
      else:
          release_payload(cur)              // dead off-heap stub; drop its ref;
                                            // a Resource's last ref queues (destructor, payload)
      cur = next
  young head = null
  old head = new_head                       // survivors are old

A minor sweep is O(young BinRefs and resource stubs), so a young view of an old BinRef costs it nothing; a major sweep is O(all stubs on this heap), not O(heap size). A gift's off-heap prefix is spliced onto off_heap_head when it is grafted, so the next minor sweeps it. A dead old Resource queues its destructor at the next major collection, and a young or received one at the next minor.

A dead Resource's destructor is fz code, so it never runs inside the sweep. The destructor is a literal closure that captures nothing, held by the shared off-heap Resource, so it lives outside every heap and nothing about it is forwarded or searched for. Each stub is visited once, by the sweep, which queues (destructor, payload) on heap.pending_dtors for the resource whose last reference it dropped; the payload is the raw integer, boxed on the process heap only when the scheduler dispatches the destructor. A process that halts takes the same sweep without a collection: Heap::release_resources_at_exit decides every stub on every chain with nothing live and copies nothing. Heap::drop releases only what a process still holds when the program tears it down without having exited, such as one parked on a receive; no destructor closure runs for those.

7. Scheduler dispatch

Dispatch order

  1. resume the runnable closure
  2. sched_core::end_quantum(scheduler, process):
       disposition = requeue (runnable), parked (blocked on a receive) or exited
       if heap.should_gc and the process did not exit:
         process.collect()          (the JIT emits fz.runtime.gc)
       clear yield reasons
       exit: mark Exited; release the off-heap chains with nothing live
       run each queued resource destructor as fz code, oldest first
  3. Requeue: re-enqueue.  Parked: wait for a send or the timer.  Exited: done.

  (The JIT, AOT and interpreter schedulers all run step 2 after every quantum,
  in every state. The interpreter never yields, so it reaches it at a park or
  an exit.)

8. Message passing — copy, self-send, share

Cross-process send

send is an any boundary. The caller passes a AnyValueRef. If the caller only has a known raw integer or float, it boxes that scalar first; a known atom becomes its ref with no box; if it already has a heap-object ref, it passes the ref as is.

When sender and receiver are different processes, the sender does all the work and never writes into the receiver's heap. sched::probe_sender tests the message against the receiver's parked matcher, if it has one, with the sender as the allocating process. It then opens a gift window on its own heap and deep-copies what the receiver will keep: the values the winning clause bound on a hit, the whole message on a miss. A hit that binds nothing opens no window and gifts an empty segment. Heap objects are copied by layout, a list spine cell by cell; scalar boxes are copied as scalar boxes and are not scanned as child pointers; an atom ref crosses as it is. The segment is queued on the receiver's in_queue with its payload, and a hit makes the receiver runnable.

The receiver drains every queued segment as the first act of its next dispatch, before any of its code or a collection runs. A miss payload joins the mailbox with its segment and waits there outside the heap; the hit payload's segment is grafted and finishes the receive, building the outcome closure on the receiver's own heap over the gifted bound values. A receiver whose receive is already matched is not probed again, so there is at most one match in its queue. A receiver that exits with gifts still queued, or messages still waiting in its mailbox, drops them: each un-grafted segment returns its block to the pool and releases its stubs' references.

Self-send (same process)

A process sending to itself copies the message into a gift on its own heap, as a send to another process does, and the segment waits in its own mailbox (sched::self_send). The sender is running, so it cannot be parked, and the push is the whole delivery. The mailbox is no collection root: the copy lives in its segment outside the heap until a receive takes it, so it survives any collection even if the sending code no longer holds a reference. The mailbox holds no reference to anything the sender holds, so no cell the sender rewrites is also held by the mailbox.

BinView — bytes are shared, not copied

When deep_copy_any_value_ref reaches a BinView (a view whose BinRef points into the shared zone), it does not copy the bytes. Instead:

  shared_bin_freeze(src.binref.shared_ptr)  // closes spare room; a buffer with none is only read
  shared_bin_retain(src.binref.shared_ptr)  // atomic ++ on refcount
  dst_binref = alloc_binref(dst_heap, shared_ptr)
  dst_view = alloc_view(dst_heap, dst_binref, src.bytes_ptr, src.bit_len)

The gift gets a fresh 16-byte BinRef and a 32-byte BinView for each view it copies, viewing the same window of the same SharedBin, and the receiver's heap adopts them with the segment. The SharedBin's refcount is now one higher. The bytes themselves never move. A 1 MiB binary sent to 100 receivers exists once in memory, with 101 references to it (sender + 100 receivers).

A BinRef is a library card and a BinView is a bookmark in the book it names. Sending one doesn't photocopy the book — it just hands out another card and a bookmark for the same book on the same shelf.

9. The shared zone — refcounted off-heap binaries

Large binaries don't live on any process heap. They live in the shared zone: individually-allocated structs scattered through the system allocator, each carrying an atomic refcount, its bytes, and its own destructor function pointer. When the refcount hits zero, the destructor runs and the memory goes back to the system allocator.

No central registry. No mutex. Each heap-backed SharedBin is one allocation: this header, then its bytes, then room, then a trailing NUL:

  struct SharedBin {           // 40 bytes of fields, 48 with alignment padding
    refcount:   AtomicUsize,                    // 0..8
    bytes_ptr:  *const u8,                      // 8..16  → the bytes just after this header (heap-backed)
    bytes_len:  usize,                          // 16..24
    destructor: fn(*mut SharedBin),             // 24..32
    room:       usize,                          // 32..40 capacity and frozen flag
  }

The struct is 16-byte aligned, the same as everything on the process heap, and that is load-bearing rather than cosmetic. A BinRef keeps this address in its first word, and the first word is also where the collector writes a forwarding marker — a pointer with a set low nibble. At 8-byte alignment about half of all SharedBin addresses have a set low nibble, so a perfectly live BinRef would read as already forwarded: the sweep would take the SharedBin itself for a relocated stub and write into it. Aligning to 16 means no real address can ever be mistaken for a marker.

The bytes follow the header in the same block, so the destructor frees one allocation. The block is never reallocated; a result that outgrows its room is a new block. A compiler-baked static SharedBin keeps its bytes elsewhere in .data, which is why bytes_ptr remains a field. The destructor field is set at allocation time:

  • shared_bin_destructor_heap — for runtime-allocated bins; frees the one block holding header and bytes.
  • shared_bin_destructor_noop — for compiler-baked static bins whose bytes live in .rodata; the destructor is reachable in principle but pinned by a static refcount of 1 so it never actually fires.

How a process points at one — BinRef and BinView

A process can't hold a raw *mut SharedBin directly; the GC wouldn't know what to do with it. Instead, each heap holds one small object per buffer and every value names it through a view:

  BinRef (16 bytes, one per buffer per heap):

  ┌───────────────────┬───────────────────┐
  │  shared_ptr (8)   │  off_heap_next (8)     │
  │  → SharedBin      │  → next BinRef    │
  └───────────────────┴───────────────────┘

  BinView (24 bytes of fields in a 32-byte slot, one per value):

  ┌───────────────────┬───────────────────┬───────────────────┬─────────┐
  │  header (8)       │  bytes_ptr (8)    │  binref (8)       │ pad (8) │
  │  window's length  │  window's first   │  → this heap's    │         │
  │  in bits << 4     │  byte             │    BinRef         │         │
  └───────────────────┴───────────────────┴───────────────────┴─────────┘

The BinRef holds the heap's one retain of the SharedBin and is the only binary object on the off_heap_head chain. BinView refs use the heap-object TAG_BINVIEW kind and BinRefs TAG_BINREF. The binref word (offset 16) is the one pointer in a view the collector follows; bytes_ptr points outside any heap arena and is never traced.

The off_heap_next link at +8 of a BinRef makes BinRefs their own intrusive linked list. When a BinRef survives, Cheney writes only a forwarding marker (to-space address with a set low nibble) at +0; +8 is left intact so the off-heap sweep can continue through the from-space chain. A live view's traced binref word is rewritten to the BinRef's to-space copy, which is made once however many views name it. A minor collection leaves an old BinRef where it is, so a young view of an old BinRef reads the buffer unchanged.

Allocation policy

When code constructs a bitstring, Heap::alloc_bitstring picks the storage based on size:

  if bytes.len() > SHARED_BIN_THRESHOLD_BYTES {   // = 64
      shared_ptr = shared_bin_alloc(bytes);
      return self.alloc_buffer_view(shared_ptr, bit_len);   // BinRef + whole-binary view
  }
  // small: inline TAG_BITSTRING object on the process heap

Render, bit-matching, and equality all go through small dispatch helpers (bitstring_bit_len, bitstring_byte_ptr, is_bitstring_like) that read from the right place based on the ref's high-bit kind tag. Callers don't know or care which storage they're looking at — the behaviour is identical.

Matching a tail copies nothing

A BinView doesn't name "the shared binary" — it names a byte-aligned window of one: its own bytes_ptr and bit_len. The whole binary is simply the window at the buffer's start spanning it.

That is what makes a byte scanner cheap. This clause asks for a tail:

  defp walk(<<_c, rest :: binary>>, n), do: walk(rest, n + 1)

so rest is not built at all while it is only matched and measured: it travels as a cursor, the source binary plus the bit position the rest starts at, and each step moves the position. byte_size(rest) is the source's length minus that position. Only a use that needs a real binary (storing it, sending it) makes it whole, and then rest becomes another view over the same bytes one byte further on, naming the same BinRef, and nothing is copied. Tails at or below the 64-byte threshold are still copied into an inline bitstring: at that size a copy is smaller than a view, and it keeps a short tail from pinning a long buffer alive.

Without this, each step copied the whole remainder, so scanning n bytes copied n + (n−1) + … bytes. Decoding a 919-byte JSON document copied 1.4 MB; it now copies the document once.

The trailing NUL.
Every shared buffer is allocated with one extra zero byte, so a binary can be handed to C as a NUL-terminated string without copying. A window that ends where the buffer's written bytes end has that NUL right after it; any other window has the parent's next byte there, and handing it to C copies it into a fresh binary first (BinView::ends_at_buffer_end tells the two apart).

Lifetime — retain, release, sweep

Three operations move the refcount:

  • Allocate a new SharedBin (refcount = 1). The BinRef made with it is the sole reference; views of it take none.
  • Send across processes: deep_copy_any_value_ref retains the shared_ptr (refcount ++) and allocates a fresh BinRef and BinView in the sender's gift window; the receiver adopts it when a receive takes the message and grafts the segment. Bytes don't move.
  • Die: either a BinRef fails to survive a GC (no live view names it; refcount −− in the off-heap sweep), or the entire heap is dropped (every BinRef still on off_heap_head is released by Heap::drop before the blocks return to the pool).

Release uses the canonical Arc pattern: Release on the decrement, an Acquire fence on the final 1→0 transition, then the destructor runs. Last one out turns off the lights.

Why this needs no locks.
The system allocator handles concurrent Box::new from any worker. The refcount is atomic. The off-heap chains are per-heap and per-heap is per-process, so only one worker accesses it at a time (scheduler invariant). fz values are immutable, so there are no write barriers. There is no central registry to contend on.

Object size on the process heap

Because binaries above 64 bytes go off-heap, the process heap deals only with small inline objects, cons cells, tuples, maps, closures, resources, BinRefs and BinView views — in practice well under the table's last entry (~7 MiB). When an allocation no longer fits, the heap installs a tip one table step up; an object larger than that step gets a parked block of its own, exact when it is larger than the whole table (see §3).

10. Return-demand destination planning

Return-demand destination planning is how the compiler chooses the result context for a call. A call is not only "call this function"; it is "call this function, and put the result into this typed hole." The planner records that choice, and native codegen lowers the selected calling convention. When the chosen context has to travel at runtime, that lowering becomes destination passing.

The capability has two parts: how the result is delivered, and what context is already available. A function can return a material value or return tuple fields directly, and a tail-call edge can forward the caller's own demand. The executable context plan is a typed compiler fact attached to a specific caller specialization and callsite. These are still ordinary immutable data constructions: no published tuple, list, or map is mutated after publication.

The important boundary is observability. Return-context motion may not cross an extern call, a receive, scheduler-visible process operation, halt, unknown closure call, or Process.heap_alloc_stats(). Allocation alone is not source-visible, but allocation timing becomes visible when a program reads the current process allocation counters.

Each list construction may retain an exact, traced source cell. Unchanged contents return that source even when shared. Changing the cell requires both construction-owned rewrite permission and a clear alias bit. Calls and structural tuple fields classify actual ownership as Transfer or Share; overlapping inputs and caller-retained values are shared before entering the callee. One-shot continuation roots do not independently expose the old language value.

A marked cell certifies a closed shared spine: its tail is marked too. Sharing stops at the first marked cell. Materialized list heads, tuple/struct fields, closure captures, and map keys/values publish their contained lists during their existing construction loops; there is no extra structural runtime scan.

Extern calls do not publish their arguments for alias tracking. If an extern wants to retain a value after returning, the extern must copy it.

Cross-process send is a copy boundary, not an alias boundary. The sender deep-copies the message graph into a gift before queueing it on the receiver, so the sender's list cells need not be marked aliased just because they were sent. A singly copied list can remain unshared; copied container fields protect sharing in the receiver. A copy keeps no record of what it has copied, so a subterm the message holds twice arrives as two separate copies. Self-send copies too: the copy waits in the sender's own mailbox. Inside a single heap the alias bit is one-way, so a rewrite miss falls back to allocation rather than rewiring a value another observer may still hold.

11. Heap allocation stats

Each process heap records allocation requests by kind. The counters are runtime process facts, separate from compiler2 telemetry, which reports compiler decisions. They are reset after process setup, so bootstrap wiring does not pollute fixture baselines. Static closures and halt continuations are read-only data in the compiled program, not heap allocations, so they never appear in the counters.

Process.heap_alloc_stats() exposes the current process snapshot as a map. The runtime reads the counters first and then allocates the map, so the returned value does not count itself. A later stats call can include the map allocated by an earlier stats call.

The total keys are :allocs and :bytes. Per-kind keys use the pattern :K_allocs and :K_bytes, where K is one of list_cons, struct, closure, continuation, map, bitstring, binview, binref, shared_bin, scalar_box, resource, or other. Heap object bytes are 16-byte aligned request sizes. The closure row counts closures a program makes; the continuation row counts the frames native code builds for calls that return to a caller, and the interpreter builds none. The counts are allocations: a continuation frame that resumes as the newest heap object is given back and stays counted.

:shared_bin_allocs and :shared_bin_bytes count the off-heap byte buffers behind large binaries, and are deliberately NOT part of :allocs / :bytes — those bytes never live on the process heap. They are the counters that tell copying from sharing: a BinView view costs the same either way, so without them a binary copied byte for byte looks identical to one that shares an existing buffer.

The stats answer "how much memory did this process request from the runtime allocation paths?" They do not answer "how many bytes survived GC" or "what did the compiler decide to lower." Use GC stats for live-set facts and compiler stats for lowering facts.

Bytes in use, idle and at peak

Peak resident memory is a poor measure of what a program uses: the system allocator takes memory eagerly and returns it slowly. The runtime counts its own bytes instead, on the thread that runs the program:

  • in-use bytes: the capacity of every block the pool has handed out and not had returned (heaps, gift segments, pooled blocks and exact-size blocks alike) plus the bytes of every off-heap binary block not yet freed: header, bytes and trailing NUL;
  • idle bytes: the capacity of the blocks resting in the pool's free lists;
  • peak in-use bytes: the most in-use bytes any allocation has reached, checked at every allocation rather than only at collections.

Every fz.runtime.gc event carries in_use_bytes and idle_bytes as they stand when that collection finished (the writer reads the pool while the from-space is held and subtracts it, so the figures are those of the pool once the from-space is released), and fz.runtime.run_ended carries in_use_bytes, idle_bytes and peak_in_use_bytes. A binary's bytes stay in use until the collection that sweeps its last BinRef frees the buffer.

12. Generational collection

Flat Cheney collection re-copies the entire live set on every cycle: a loop that builds a list of 1000 elements would copy 100 + 200 + … + 1000 bytes, O(N²) in total, if GC fired every 100 allocations. The heap avoids that by splitting into young and old blocks (see §4). A minor collection copies only the young blocks; the list tail, allocated many cycles ago, is not re-copied. Total copy work for a heap that keeps a thin slice of what it allocates is proportional to what it keeps.

Why fz needs no write barrier

Generational GC normally requires write barriers: if an old object is mutated to point at a new object, the GC must record it (otherwise the new object looks unreachable from the old generation). Every pointer write needs an extra store — significant overhead.

fz data is immutable, with one exception the runtime controls: a list cell or struct nobody else holds may be reused in place when a list is rebuilt or a struct updated. A collection marks every list cell and struct it keeps as shared, and a gift's are marked shared when they are copied into it, so a shared one is never reused. An old object therefore never gains a reference to a younger one. No write barriers needed.

A minor collection traces from the same roots as a major one, skips any reference that points into an old block, and copies the young objects it reaches. Its survivors fill new old blocks. A major collection runs when old bytes pass twice what the last major left, and is the only pass that reclaims old data. A debug assertion classifies every reference the collector meets as a literal, a from-space object or an old object, and fails on anything else.

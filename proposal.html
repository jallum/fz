Compiler2 Runtime Value Demand

A design proposal for replacing broad callable recovery with one explicit demand model for values, returns, parameters, and callable materialization.

1. Goal, signal, strategy

Goal

Compiler2 should publish exactly the runtime work demanded by the closed program. Constructing, passing, returning, storing, or calling a callable value should not by itself create callable entries, native callable boundaries, closure allocations, or ABI lanes unless the runtime representation is actually needed.

Signal

The artifact ladder should show no callable entries for unused callable constructors, no native callable boundaries unless a callable value escapes or is called opaquely, no hidden type-based recovery, and unchanged quicksort tuple-field delivery. Telemetry should expose demand counts directly.

Strategy

Lift the existing return-demand idea into a general runtime value-demand projection over the closed lowered value graph. Derive ABI lanes, callable entries, native boundaries, and closure materialization from that projection.

Core rule: semantic facts say what values mean. Runtime demand says which values must physically exist. Callable boundaries are derived from runtime demand, not recovered from callable-looking types.

2. Code read before designing

The relevant implementation already contains most of the raw information. The problem is that the information is split across local mechanisms and then partially thrown away.

AreaRelevant codeWhat it proves
Semantic activation walk src/compiler2/jobs/semantic.rs, especially analyze_activation, resolve_closure_call, runtime_callable_boundary_values Compiler2 discovers exact callsites and closure-call surfaces on CallTargetSummary.surface_inputs, then collapses callable materialization to runtime_callable_values: Vec<ValueId>.
Semantic facts src/compiler2/semantic.rs ActivationAnalysis stores reachable clauses, callsites, latent executables, runtime callable values, and value types. It does not store exact runtime demand.

Artifact projection src/compiler2/jobs/artifact.rs ABI-ready currently derives parameter lanes from semantic activation inputs, return ABIs from ExecutableNeed, and callable entries by re-reading callable types from runtime_callable_values.
Backend handoff src/compiler2/jobs/backend.rs entry_input_abis is already a small backward demand engine for delivered resume values. It should become part of the general demand projection instead of staying local.

Native codegen src/compiler2/native_codegen/prim.rs, src/compiler2/native_codegen/terminator.rs, src/compiler2/native_codegen/driver.rs Codegen already wants settled callable-boundary ids and exact closure-target surfaces. It should consume explicit facts, not re-select obligations.

3. Current model and the bug

The current compiler2 path discovers more than it preserves.

AnalyzeActivation
  -> resolves direct call targets
  -> resolves closure-call targets and exact surface inputs
  -> sees callable-looking arguments and escaping callable-looking returns
  -> stores only runtime_callable_values: Vec<ValueId>

DeriveAbiReady
  -> for each runtime callable value
  -> read the value type
  -> enumerate callable clauses from that type
  -> publish CallableEntry records

LowerNativeProgram
  -> materialize every FunctionRef / Lambda step
  -> choose a NativeCallableBoundary by function + capture type
The bad recovery step is type-shaped, not use-shaped. Types can say a value could be callable. They cannot say this particular runtime program needs a callable object, callable entry, wrapper function, closure environment, or ABI lane.

The bug in the narrow ticket is visible here:

fn ignore(_fun), do: 0

fn main() do
  fun = fn x -> x + 1 end
  ignore(fun)
end

The exact semantic fact is "the value fun flows to ignore/1 input 0." The runtime fact is "that input is never read." Current compiler2 turns the first fact into a callable entry because the input type is callable-shaped. That is the modeling error.

4. The design decision

The good decision is to make runtime value demand first-class, using the lowered value graph and the closed call graph we already have.

This is not a new callable subsystem. It is the generalization of the mechanism quicksort already depends on: ExecutableNeed::TupleFields(2) tells partition/4 to deliver fields instead of a heap tuple. The same idea should apply to function parameters, resume values, call arguments, tuple producers, and callable producers.

Separate these facts permanently:

FactMeaningOwned by
Semantic evidence Activation input types, reachable clauses, selected callees, exact closure-call targets, return type evidence. AnalyzeActivation
Runtime demand Which values must exist at runtime, in what shape, and which callable uses require first-class representation. Root-scoped demand closure over the closed executable graph.
Representation ABI lanes, callable entries, native callable boundaries, direct closure-call operands, and closure materialization. Artifact/backend/native projections derived from demand.

5. Data structures

The names below are proposal names. The important part is the shape: demand is a finite lattice over values, and callable demand is one variant inside it.

pub enum RuntimeDemand {
    Ignore,
    Value,
    TupleFields(Vec<RuntimeDemand>),
    Callable(CallableDemand),
}

pub struct CallableDemand {
    pub resolved: BTreeSet<CallableSurface>,
    pub opaque: bool,
    pub escape: bool,
}

pub struct CallableSurface {
    pub inputs: Vec<Ty>,
}

pub struct ExecutableRuntimeDemand {
    pub return_demand: RuntimeDemand,
    pub input_demands: Vec<RuntimeDemand>,
    pub value_demands: HashMap<ValueId, RuntimeDemand>,
    pub call_arg_demands: HashMap<CallSiteId, Vec<RuntimeDemand>>,
    pub callable_materializations: HashMap<ValueId, CallableMaterialization>,
}

pub enum CallableMaterialization {
    DirectOnly { surfaces: BTreeSet<CallableSurface> },
    FirstClass { surfaces: BTreeSet<CallableSurface> },
}

pub struct RuntimeParamLayout {
    pub inputs: Vec<RuntimeInputLayout>,
    pub reprs: Vec<AbiValueRepr>,
}

pub enum RuntimeInputLayout {
    Omitted { semantic_index: usize },
    Value { semantic_index: usize, repr: AbiValueRepr },
    TupleFields { semantic_index: usize, fields: Vec<RuntimeInputLayout> },
    DirectCallableCaptures { semantic_index: usize, captures: Vec<RuntimeInputLayout> },
}

The exact Rust shape may collapse some of these. The invariant must not collapse:

Invariant: ActivationKey.input remains semantic. Runtime parameter layout is derived. The number and order of semantic activation inputs no longer defines the native/interpreter ABI.

Demand join

Ignore + D                         = D
Value + anything                   = Value
TupleFields(a) + TupleFields(b)    = TupleFields(join_fields(a, b)) when arities match
TupleFields(_) + other             = Value
Callable(a) + Callable(b)          = Callable(join_callable(a, b))
Callable(_) + TupleFields(_)       = Value
Callable(_) + Value                = Value

CallableDemand can hold more than one resolved surface. Two exact direct calls to the same lambda do not automatically force a heap closure. opaque or escape does.

6. Algorithm

The demand solver runs over a settled root and its closed executable graph. It is monotone and finite.

6.1 Build producer and consumer indexes

For each reachable executable, index the lowered body:

ValueId -> Producer

Producer::Input(index)
Producer::EntryInput(entry_id)
Producer::Const
Producer::Tuple(items)
Producer::List(items, tail)
Producer::Map(entries)
Producer::MapUpdate(base, entries)
Producer::FunctionRef(function)
Producer::Lambda(function, captures)
Producer::Op(inputs)
Producer::Projection(source)
Producer::CallResult(callsite)

This index is already implicit in LoweredStep, LoweredTail, and the current collect_step_reads helpers. The proposal makes it explicit once.

6.2 Seed demand

Each executable starts with the demand from its key:

ExecutableNeed::Value
  -> RuntimeDemand::Value

ExecutableNeed::TupleFields(n)
  -> RuntimeDemand::TupleFields(vec![Value; n])

Then seed runtime boundary requirements:

BoundaryDemand
Extern callEvery extern argument is Value. The C boundary is opaque.
Provider boundary callEvery argument crossing the provider boundary is Value.
Entry dispatchInputs/projections/pinned values used by dispatch are Value.
Receive/send/spawn/dbgPublished values are Value. Callable values published here get escape = true.
Closure call with exact targetCallee gets CallableDemand.resolved(surface). Runtime args get demand from target input demand.
Closure call without exact targetCallee gets opaque = true. Runtime args are Value.

6.3 Propagate backward through producers

demand(value, D):
  old = value_demands[value]
  new = join(old, D)
  if new changed:
    work.push(value)

while work not empty:
  value = work.pop()
  demand = value_demands[value]
  producer = producers[value]

  match producer:
    Input(i):
      input_demands[i] = join(input_demands[i], demand)

    Tuple(items):
      if demand is TupleFields(fields):
        demand each item with matching field demand
      else if demand materializes the tuple:
        demand each item as Value

    Lambda(function, captures):
      if demand is Callable(resolved only):
        for each resolved surface:
          demand captures using target activation input demand
      else if demand requires first-class callable:
        demand captures as Value
        record callable materialization

    FunctionRef(function):
      if demand is Callable(resolved only):
        record direct callable use
      else if demand requires first-class callable:
        record callable materialization

    List / Map / Struct / Bitstring:
      if demand is Value:
        demand contained runtime values as Value
      else:
        use only supported projection demands; otherwise widen to Value

    Projection(source):
      demand source enough to perform the projection

    Op(inputs):
      demand inputs as Value

6.4 Propagate across calls

The demand solver is root-scoped, just like SealSemanticClosure. It already walks ExecutableKey today, so it is the right place to generalize.

for each callsite in executable:
  callee = materialized call edge
  callee_return_demand = destination demand at this callsite
  enqueue ExecutableKey { activation: callee.activation, need: callee_return_demand }

  for each source argument:
    source_arg_demand = callee.input_demands[arg_index]
    demand(source_value, source_arg_demand)

This is a fixpoint because callee input demands are learned from callee bodies, and caller argument demands depend on them. The lattice is finite: each executable has finite values, finite callsites, finite tuple arities, and finite callable surfaces discovered from the program.

6.5 Derive representation

Only after demand settles:

Runtime demand plan
  -> runtime param layouts
  -> value reprs
  -> callable entries
  -> backend call arguments
  -> native callable boundaries
  -> closure materialization

Callable-entry ABI is a publication contract for first-class callable values. It is not the internal ABI for direct executable calls.

7. Worked examples

7.1 Unused callable constructor

fn ignore(_fun), do: 0

fn main() do
  fun = fn x -> x + 1 end
  ignore(fun)
end
StepDemand factResult
Analyze ignore/1Input 0 has semantic type closure_lit(lambda).No runtime read of input 0.
Demand ignore/1input_demands[0] = Ignore.No ABI lane for _fun.
Propagate to callerfun receives Ignore.Lambda producer has no runtime demand.
Artifact resultNo materialized callable value.No lambda executable, no callable entry, no native boundary, no closure allocation.

This fixes the current failing invariant without special-casing callable arguments.

7.2 Direct call of a captured lambda

fn apply(fun), do: fun.(41)

fn main(a) do
  fun = fn x -> x + a end
  apply(fun)
end
StepDemand factResult

Pressure point: today BackendTail::ClosureCall names a callee value, and native codegen's direct fast path still passes a self closure pointer. This design requires the backend artifact to distinguish direct callable operands from first-class callable operands. That is not optional.

7.4 Quicksort

fn partition(_, [], lo, hi), do: {lo, hi}
fn partition(p, [h | t], lo, hi) when h < p, do: partition(p, t, [h | lo], hi)
fn partition(p, [h | t], lo, hi), do: partition(p, t, lo, [h | hi])

fn qsort([]), do: []
fn qsort([p | rest]) do
  {lo, hi} = partition(p, rest, [], [])
  append(qsort(lo), [p | qsort(hi)])
end

Demand flow:

main return                         Value
qsort return                        Value
qsort -> partition call result      TupleFields([Value, Value])
partition base tuple {lo, hi}       TupleFields([Value, Value])
partition recursive tail call       TupleFields([Value, Value])
qsort continuation after partition  receives lo, hi as lanes; captures p
append / qsort recursive calls      Value

Nothing in this path is callable. That is the point: the same demand model preserves the existing quicksort win without knowing about callables.

Existing contractDemand explanation
partition/4 uses TupleFields(2)The caller destructures the result, so the tuple object is not demanded.
Continuation has two result lanes plus pivot captureThe delivered resume value demand is field-shaped, and the remaining live value is p.
No ListTail demandReusable-cons capability stays a physical ownership fact, not a semantic demand variant.
No callable inventoryNo callable value receives escape or opaque demand.

9. Code changes

9.1 Semantic layer

Keep semantic analysis focused on meaning and exact call facts.

ChangeWhy
Remove ActivationAnalysis.runtime_callable_values It is a lossy representation fact stored in the semantic layer.
Keep CallTargetSummary.surface_inputs It is already the exact semantic callable surface we need, nested under CallSiteSummary.targets.
Keep value types Demand derivation needs type evidence to project tuple fields and callable captures.
Stop resolving escaping/materialized callable activations inside AnalyzeActivation Escapes depend on runtime demand, which is executable/root-specific.

9.2 Root closure and demand closure

Generalize the existing executable traversal in SealSemanticClosure.

FactKey::SemanticClosed(root) stores SemanticClosure today:
  entry: ExecutableKey
  activations: HashSet<ActivationKey>
  executables: HashSet<ExecutableKey>

Proposed:
  entry: ExecutableKey
  activations: HashSet<ActivationKey>
  executables: HashSet<ExecutableKey>
  runtime_demands: HashMap<ExecutableKey, ExecutableRuntimeDemand>

The closure sealer becomes the place where runtime demand can grow the executable frontier. That is already its job for tuple-field return demand.

9.3 Artifact layer

CurrentReplacement
param_reprs = activation.input.map(abi_value_repr) Derive RuntimeParamLayout from input_demands.
runtime_callable_values copied through artifacts Carry ExecutableRuntimeDemand and derived callable materializations.
derive_callable_entries resolves entries from types Derive entries only from first-class callable materialization demand.
entry_input_abis recomputes resume demand in backend lowering Move this demand into the shared demand plan so backend and native consume the same fact.

9.4 BackendProgram

BackendProgram is the shared interpreter/native handoff, so it should carry demand-shaped operands.

BackendCallArg today:
  value: ValueId

BackendCallArg proposed:
  source: RuntimeOperand

RuntimeOperand:
  Value(ValueId)
  TupleFields(Vec<RuntimeOperand>)
  DirectCallable { function, captures: Vec<RuntimeOperand> }
  FirstClassCallable(ValueId)

The exact enum can be smaller, but the split is essential. A direct callable operand is not a closure ref. A first-class callable operand is.

9.5 Native lowering and codegen

ChangeWhy
Stop scanning all lambda/function-ref steps for callable identities Only first-class callable materialization needs a callable identity wrapper.
Stop calling settled_callable_boundary by capture type The boundary id should be an artifact fact attached to the materialized value.
Lower direct callable calls without a heap closure when demand permits Resolved callable demand already names target and capture operands.
Keep callable-entry ABI separate from executable-internal direct ABI Callable entries are publication wrappers for first-class callable values only.

9.6 Backend interpreter

The interpreter must consume the same BackendProgram facts. It should not eagerly create AnyValue::FnRef or heap closures for every callable producer.

ProgramStep::Lambda today:
  make_closure(...)

After demand:
  DirectOnly       -> bind a direct callable descriptor or no value at all
  FirstClass       -> make_closure(...)
  Ignored          -> no binding required unless later structural demand exists

10. What gets removed

  • ClosureBoundaryUse::CallableArg. It is the broad recovery bug under a different name.
  • runtime_callable_boundary_values, note_callable_arg_uses, and closure_value_needs_runtime_boundary.
  • resolve_materialized_runtime_callable_boundary_activations and type-driven callable activation recovery for materialized values.
  • ABI-ready callable entry derivation from arbitrary callable value types.
  • Native callable boundary selection from capture types.
  • Native callable identity collection from all callable-producing steps.
  • Backend-local resume demand recomputation once the shared demand plan exists.
  • The assumption that every semantic activation input is a runtime ABI lane.

11. Why this works

11.1 It is finite

For one settled root, the graph is finite:

  • Finite executables in the semantic closure.
  • Finite lowered values per executable.
  • Finite tuple arities present in source and demand sites.
  • Finite callable surfaces from resolved callsites.
  • A finite demand lattice with Ignore as bottom and Value as conservative top.

Every propagation step only joins demand upward. Therefore the demand fixpoint terminates.

11.2 It is conservative

Every runtime read seeds demand. If the compiler cannot project a narrow demand through a producer, it joins to Value. That may keep a value alive, but it cannot remove a needed runtime value.

11.3 It preserves semantic precision

Semantic activation keys do not shrink when runtime parameters shrink. Dispatch, contracts, recursive keying, and return typing still see the full semantic input vector. Runtime ABI layout is a derived representation, not identity.

11.4 It removes the bad recovery path

No later stage asks, "Does this type look callable?" to decide runtime obligations. Later stages ask, "What did the demand plan say this value must be?" That is the correct boundary.

11.5 It generalizes quicksort instead of threatening it

Quicksort is already a proof point. TupleFields(2) is a runtime demand that avoids tuple allocation. General runtime demand keeps that behavior and uses the same machinery to answer callable questions.

12.4 Fixture contracts

  • Quicksort keeps partition under tuple-field return demand and keeps callable inventory empty.
  • Enum reducer fixtures keep the required callable entries, but only where the callable is actually first-class or opaque.
  • Unused callable constructor fixture stays cold below semantic analysis.
  • Closure allocation telemetry drops for direct-only callable paths and stays nonzero for escaped callable paths.

Conclusion

The smallest correct model is not a callable patch. It is a runtime value-demand model over the lowered value graph. The compiler already has the expensive facts: exact callsite summaries, exact value producers, semantic activation keys, and a working tuple-field return-demand example in quicksort. The clean move is to keep those facts intact, compute demand once at the root artifact boundary, and let representation fall out mechanically.

Acceptance contract: no runtime object, ABI lane, callable entry, native callable boundary, or closure allocation exists unless a settled demand fact requires it.
